01 · 约 5 分钟

为什么现在做工具层，而不是继续加功能？

已经能列目录、读文件了，为什么还要设计这一层？

上一步证明“模型能借工具做事”；这一步要证明“增加一种动作时，原来的循环仍然通用，用户也能理解并控制它”。

先看两个阶段的差别

假设目前只有查看目录和读取文件。主程序可以分别写两段特殊处理：遇到第一种就列目录，遇到第二种就读文件。数量很少时，它能工作。

现在加一个“写总结文件”。它除了执行，还要说明写到哪里、是不是覆盖旧文件、用户是否同意。如果这些都继续塞进主循环，每加一种工具，主循环就得认识更多细节。

工具设计的原文诊断是：两个工具硬编码在主循环中，通过 isinstance(tool, DirectoryTools) 分路，目录发现权限逻辑也在循环里。isinstance 在这里是“判断它是不是某个具体类型”的代码写法；你只需理解，它使总控依赖了具体工具。

这次究竟补哪三个缺口？

  1. 能扩展：第三个工具接进来，不再为它修改主循环里的专用分支。
  2. 能说明：用户看见“读取 plan.md”，而不只是持续转圈；写入时看见具体后果。
  3. 能控制：参数错误、权限、用户拒绝、超时和失败都有明确处理。

原文还把统一 Tool 对象视为后续记录 ToolCall、做会话持久化、挂载风险等级的基础。“现在只有两个工具，重构成本最低”是设计者的阶段判断，不是已量化的成本结论。

教学解释 · 定位

整个项目仍叫 Local Agent Runtime，目标是掌握模型之外的运行、工具、安全、状态与扩展工程，并形成可演示的求职作品。工具层是其中一部分，不是把整个项目缩成三个文件函数，也不是先做一个漂亮聊天框。

会议强调：不管后续方法包或外部能力怎么接入，实际动作最终需要具体工具完成。工具设计开头强调工具层“唯一的产品价值”在用户何时被打断、看见什么。这里保留它的产品重心，但不能据此删去总设计中的安全、执行可靠性和可追踪性。

开发检查点

先能说出“现在的耦合在哪里、这次解除什么耦合”，再讨论增加工具数量。能运行两个工具，不自动等于工具层抽象已经成立。

02 · 约 8 分钟

先陪它完成一次任务，再给这些步骤起名字

你说“读资料、写总结”之后，中间到底发生了什么？

教学解释 · 贯穿实例

假设用户说：“查看工作区 docs 里的计划，整理项目结论，保存到 docs/summary.md。”例子路径来自工具设计的文件场景；以下调用 ID、正文和步骤为教学构造，不是实际执行记录。第一次请求不偷放文件正文。

第一步：模型知道“有工具”，还不知道“文件写了什么”

程序把你的要求、做事规则，以及可以使用的工具说明发给模型。说明里有“列目录”和“读文件”，但没有自动附上电脑里所有文件的内容。

模型决定先提出：list_files({"path":"docs"})。这是一张请求单，不是目录已经列出来了。

第二步：程序接手，工具才真正访问文件系统

程序查工具是否存在、参数是否符合规则、目录是否在允许范围内。通过后，调用实际列目录的函数。结果返回：“发现 plan.md”。用户可以看到“查看 docs/ 目录”。

程序把“模型刚才请求了什么”和“实际返回什么”一起加入下一次模型输入。模型这时才有依据知道该读哪个文件。

第三步：模型再请求读取，正文读完再送回来

模型提出 read_file({"path":"docs/plan.md"})。程序再次校验并执行，得到示例正文：“项目代号：青禾-47；评审人：林工”。这一结果也要送回模型，模型才能据此整理总结。

第四步：模型提出写入，但还没有写入

模型提出 write_file 请求，参数带目标路径和拟写入内容。程序核实文件是否存在，形成“新建什么/覆盖什么”的说明与预览，进入审批。此时界面显示等待你确认，不能显示“已保存”。

第五步：同意、拒绝、失败，都会改变后面怎么走

你同意：在本次授权范围内执行写入，记录真实结果，再据结果汇报。你拒绝：不执行这次写入，记录拒绝，不能悄悄换一个路径继续写。磁盘满：如实告诉你需要处理环境，不能无限换参数重试。

第六步：任务有证据地结束

“我准备写”不是成功，“调用过写工具”也不是成功。至少要有实际写入结果，才能说已保存；如本次验收要求复读文件，还须完成那项验证。不能写入时可以明确结束为“总结已形成，保存未完成”。

现在再认识三个名字

名字刚才的哪一段不要混淆
Model Call
一次模型调用		程序发一份输入，模型回一份输出。一条用户任务可能包含多次。
Turn
一轮用户交互		会议里指你提交一次消息，到 Agent 最终回复的整轮。不是一次工具执行，也不一定只有一次 Model Call。
AgentRun
一次运行		系统为这次任务管理执行、等待、失败、取消和结束。Turn 是交互口径；AgentRun 是程序记录的运行对象，不能不看设计就处处画等号。

反复“请求模型 → 执行动作 → 送回结果 → 再请求模型”的过程，就是 Agent Loop。把这次运行撑起来的规则、工具执行、状态与记录机制，合起来理解为 Runtime。

会议的“每日金价”演示怎样对应这里？

会议展示的是另一套系统的完整轨迹：定时任务进入，先做 Memory Recall（查找可能有用的已有记忆）；任务简单，所以没有召回。周报任务则可能召回本周工作消息。随后有技能解锁/加载、Model Call、工具请求与结果回填，取得数据后汇报金价，最后可能写回值得保存的记忆。

其中 read_skill 本身也是一个工具：模型看到定义后发请求，程序读回方法说明。这个演示帮助你理解数据流，不表示当前项目已经有定时任务、技能或长期记忆。不应为了复现整个演示先把这些全部做出来。

开发检查点

检查一份记录时，逐次指出：模型请求、实际执行、实际结果、下一次模型输入、结束依据。少一段，就不能仅凭最终回答判断完整链路。

03 · 约 8 分钟

模型这一轮看见什么：请直接展开这份输入包

为什么同一个 Agent 里，模型也不能凭空知道刚才的工具结果？

Context 就是本轮实际发给模型的材料。不是电脑上所有东西，不是会话库存的全部记录，也不是模型自动拥有的记忆。

先从第二次调用看起

第一次模型请求列目录。现在目录已经返回，第二次请求应把以下内容送进去。这个图只解释内容关系，不绑定某家 API 的字段格式。

本轮 Context（输入包）
├─ Tool List：目前可用工具的名字、用途、参数规则
└─ Message List：按顺序组织的消息
   ├─ system：做事规则，如只能访问授权工作区
   ├─ user：查看 docs 的计划，整理并保存总结
   ├─ assistant：请求 list_files，参数 path=docs，调用 ID=c1
   └─ tool：回应 c1，实际发现 docs/plan.md

模型本轮才有依据提出：
assistant：请求 read_file，参数 path=docs/plan.md，调用 ID=c2

Message List 是消息列表，也就是这份输入中的对话与工具往来记录。Tool List 是可用工具说明清单，不是“过去用过哪些工具”的日志。两者都属于 Context，因为模型这轮确实需要看到它们。

assistant 到底是谁？

会议中你问 assistant 是否是工具里的角色。更准确地说，它是模型输出消息的角色标签：可以是给用户的回答，也可以是请求调用工具。工具执行后的反馈是另一条工具结果消息，不应混成“assistant 自己读到了文件”。

system 表示系统规则；user 表示用户要求；assistant 表示模型输出；tool 表示程序送回的工具反馈。实际供应商可能采用不同字段或内容结构，适配层负责转换；这里教的是角色关系。

短期连续性不要求先压缩，也不要求先做长期记忆

只要程序把必要的上一轮消息、工具请求和结果重新加入下一轮输入，模型就能接着做。会话很短时，可以直接保留这些消息；材料太长时，才需要选择、裁剪或摘要。

所以“同一个 API 调了两次”并不自动产生连续性；“同一个 Agent”也不是把信息自动共享的魔法标签。要看第二次到底发了什么。某些服务可能提供托管状态，但本项目教学主线仍需明确上下文由哪一层组织，不能靠猜。

有 100 条历史，模型一定看见 100 条吗？

不一定，但也不是“一定不能”。如果本轮全选且容量允许，就可能全看见；如果只选了近期消息和摘要，就不是全量。负责选材的程序模块叫 Context Builder，直译就是“本轮输入的组装者”。

教学解释 · 选择规则示意，不是三份原文规定的算法
  1. 先保留系统规则、当前任务目标、用户限制和未完成事项。
  2. 保留下一步所需的工具定义，以及相互对应的请求和结果；不能只剩“成功了”却不知道成功的是什么。
  3. 在容量允许时加入近期完整消息；旧材料可摘要或按需再读，但不能丢失关键状态。
  4. 在记录中列出选入了什么、裁掉了什么以及 Token 用量，才能检查选择是否合理。

三份原文没有给出“固定保留最近 N 条”的数值公式。不要把示意策略当已定配置。第 11 章再把 Session、Workspace、Memory 与这份输入包放在一起比较。

04 · 约 9 分钟

工具说明、Schema、参数：分别回答三个不同的问题

“已经写好一个函数”和“模型知道如何安全请求它”，差在哪里？

描述解释用来干什么，Schema 规定请求单怎么填，参数是本次填进去的值。真正的操作仍由工具代码执行。

不要从英文开始：先看一张“读取文件申请单”

你需要知道什么示例对应名字
该选哪个动作？读取授权工作区内、已发现的 UTF-8 .md/.txt 文件。description · 用途说明
必须填哪格？怎么填？必须有 path；值是文本；不接受额外字段。inputSchema · 参数规则
这次具体读哪个？path 填 docs/plan.md。arguments / input · 本次实参
谁真正打开文件？接收路径并读取文件的程序函数。execute · 执行实现

Schema 可以理解成表单的空白格式与填写规则。它不是本次答案，不记录上次执行得好不好，也不是文件正文。输入中的描述帮助模型选对工具，规则帮助模型填对请求，两者缺一都会增加误用。

看一眼结构化写法 · 不要求记代码 
工具定义片段（教学示意；不是本仓库已实现 API）
{
  "name": "read_file",
  "description": "读取授权工作区中已发现的 UTF-8 .md/.txt 文件",
  "inputSchema": {
    "type": "object",
    "properties": {
      "path": {"type": "string", "description": "要读取的文件路径"}
    },
    "required": ["path"],
    "additionalProperties": false
  }
}

模型本次填写：
{"path": "docs/plan.md"}

type 是类型，object 是一组具名字段，properties 列字段，required 列必填项。这里只示范一种规则写法，不能把它当成完整文件权限校验。path 是文本，仍可能指向不存在或未授权的位置。

三类人看的是同一个工具的不同部分

模型要知道“能做什么、怎么填”；程序要知道“怎么执行、限时和预算怎样算”；用户要知道“为什么现在做、到底动了什么、需要我决定吗”。工具设计认为前两类已有一些支持，第三类明显不足。

工具设计要求声明读文件示例注意
名字 nameread_file用于按名找到对应实现。
给模型的说明可读范围、格式、用途不是给用户的状态文案。
给用户的一句话读取 plan.md随本次参数变化；第 08 章区分意图和后果。
风险等级授权范围内只读示例为低风险低风险不等于不校验权限。
来源内置 builtin为未来 user/MCP 留接口与展示位置。
执行方法 execute实际读取并返回前五项声明，最后一项实现；有声明不等于有能力。

总设计还明确要求 inputSchema 和 permissionLevel 等接口。工具设计的“五件事”是这一版的产品视角拆分，不是取消 Schema。两个文档侧重点不同，要一起看。

工具是临时写出来的吗？多填一个参数就多一种能力吗？

在会议讲的这条路径里，工具名、描述和参数结构是开发者预先定义并注册的；模型选择工具、填写本次值。它看到“打开页面”的动作文案，不代表它临时创造了一个新工具。以后动态加载也得先注册能力，不能绕过这个边界。

会议用“只收 URL 的工具”解释能力范围：它可以按实现去取指定页面，但不一定能凭关键词搜索未知网页。要支持关键词、页数、图片等选项，必须同时有对应的参数规则和执行实现。Schema 是能力入口的约定，不是凭空造能力的按钮。

工具、注册表、主循环：不是三个词，而是三份工作

把所有逻辑都写进主循环有什么问题？“工具自己记账”又是什么意思？

工具负责自己的动作与记录，注册表负责找到它们并汇总说明，主循环负责推进整个任务。这叫分工，不是把安全检查从程序里删掉。

先想一个正在发生的场景

已经列过 docs，刚读完第一个文件。模型还想读第二个。此时谁知道哪些目录已经发现、已经读了几个文件、还剩多少可用预算？原文要求这些工具相关状态不要继续散落在主循环里，由工具层管理自己的账。

这里的账就是执行状态记录；不是财务账本，也不是模型脑中的记忆。预算是允许使用的资源上限，例如文件数、结果长度、调用次数或等待时间，而不只是钱。

角色具体负责不应承担
Tool · 工具声明接口，执行自身动作，报告已列目录、已读文件/预算、已写文件等相关状态。替整个任务决定下一轮该问模型什么；自行扩大用户授权。
Tool Registry · 工具注册表提供本轮工具 Schema 清单；按名字查工具；汇总各工具报告的本轮状态摘要。凭名字生成工具能力；把“登记过”当成“执行成功”。
Agent Loop · 主循环问模型要动作 → 该拦就拦 → 执行 → 回填，控制继续或结束。为 list_files/read_file/write_file 各写一条专用分支。

注册表就像一本可用动作目录，但不仅保存名称：它还把动作说明提供给模型，帮助程序找到实际实现，并收集状态摘要。原文把现有状态摘要称为 scope；具体结构需看工程实现，不能把这个词理解成只含“权限范围”一个含义。

“工具自己管”为什么不等于“各做各的安全规则”？

教学解释 · 不改变原文边界

列目录与读文件有关联：读文件可能依赖“该文件已被发现”的事实。把记录搬到工具层后，仍需要在同一次运行的受限工作区中共享必要事实。不能让两个工具互相不知道，也不能把所有会话的发现结果放成一份无限共享的全局账本。

工具相关预算由工具层报告；整次 AgentRun 的最大轮数、总超时、取消与终止，仍需由运行控制层约束。原文没有规定共享状态类的名字或数据库表结构，本册不替工程师发明一个强制实现。

Tool Runtime 是不是“记日志”就够了？

会议 00:37:32 从“把每次执行状态记下来”解释工具运行时，方便先理解状态。完整的 Tool Runtime 还包括注册、参数校验、权限和审批、执行、超时/取消、结果与错误、截断和记录。它是让工具受控运行的一整段程序机制，日志只是其中一部分。

你可以把 Registry 看作“找谁来做”，把统一执行流程看作“按什么规则让它做”。二者协作，但不要把它们简单当成同一个对象；具体代码如何分文件仍是实现选择。

开发检查点

教学解释 · 本章入口

找工具查参数查权限真执行记结果

① 这个工具存在吗？

程序用注册表查 read_file。如果模型写成未注册的 create_file，就找不到。此时不会执行任何“差不多的工具”，而是生成“未知工具”的失败报告。

防的是：把模型预测出来的名字，当成一定存在的能力。

② 参数合法吗？

先检查字段名、必填项、值类型及约定范围。例如缺 path，或该填文本却填了数组。会议用 URL 没填、字段拼错、content 少一个 t 说明这类错误。

然后还要落实工具的实际约束：路径解析后是否在允许工作区，是否满足已发现文件等读取规则，文件是否存在、格式是否支持。具体检查可能分别位于统一执行器和工具内部，但不能漏掉。

防的是：“请求单填得像样”却请求了不存在、不可读或越权的目标。Schema 合法不是通行证。

③ 这次需要用户确认吗？

程序按权限策略判断：授权范围内读文件通常可自动执行；写入等操作可能要先显示后果、等你确认。需要审批时，状态变成“等待确认”，此时还没执行。

同意：在具体授权范围内继续。拒绝：生成拒绝报告，不执行这次动作。第 08 章详细解释中风险的不同口径。

防的是：模型只因觉得“有帮助”，就把动作做在用户不知情的地方。

④ 执行真实函数，但不能无限等

通过前面的检查后，程序才调用读取函数。文件内容由函数读出。读取异常、网络等待或其他工具失败都必须被接住并报告。

超时是“过了规定时间就结束等待并处理失败”；取消是“收到停止指令就停止推进，并尽可能终止正在执行的工作”。原文未给出统一时长数值，不要自行把演示数值写成配置。

会议提出可以让模型填最大等待时长。那是可选参数设计；即使采用，也只能在程序上限内申请，不能由模型把上限改成无限。对于有副作用的工具，超时也不保证动作完全没发生，要记录已知结果与未知状态，不能盲目重复写入或发送。

⑤ 更新记录，然后回填

工具层更新与本次调用相关的账，执行流程记录成功、失败、耗时及调用关联等实际信息。回填指把结果加入这次任务的消息/上下文处理链，以便下次模型调用真正收到。

失败的尝试、用户拒绝、超时同样要留可核查记录；不能只统计成功。哪类失败计入何种预算需要明确规则，原文没有给出所有计数细则。

回填之后，一定还要再问一次模型吗？

不一定。模型可以修正的错误，一般回填后继续；用户才能处理的环境问题，应停止无效循环并明确提示。已经取消、超出整轮预算或无法安全继续时，也要合理结束。保留错误记录与继续调用模型，是两件不同的事。

拒绝和取消，都要让用户知道系统真的停了

拒绝是不同意这次具体动作；取消是要求停止运行。拒绝写入后，可以如实说明未保存，是否提供不写文件的回答取决于任务与策略；不能自动把同一写入换个路径重试。取消时不能继续开启新动作，更不能把“停止等待”说成已经撤销所有副作用。

工具设计原定的三步

第一步：只搬家，不改行为

教学检查：同样允许的请求仍成功；同样被禁止的请求仍被拒绝；原调用与结果仍对应；主循环通过通用入口调用工具。原测试不改是守住行为的要求，若原有测试漏测了边界，还应依据本批风险补证据，不能单凭绿灯证明一切。

第二步：加入“归谁”和用户可见文案

统一成功/错误报告，让程序按可恢复性分流；在界面显示“读取 plan.md”这样的具体动作。

怎么看日志，而不是被日志淹没？

Event 是一步发生了什么的结构化记录；Trace 是把同一次运行的这些记录串起来。先找请求 ID、工具名、校验结果、审批结果、执行反馈、下一次输入和最后状态，再看细节。

总设计列出的事件包括 run.started、context.built、model.started、model.delta、model.completed、tool.requested、approval.required、tool.started、tool.completed、run.completed、run.failed。这些是目标事件体系，不表示本次已在程序中核实。

需要观测整条 Trace、模型/工具耗时、Token 与费用、工具成功率/失败原因、Loop 轮数、上下文构成与裁剪、取消和权限拒绝。用户可见文案帮助理解过程，但不能替代底层真实证据。

Session、Context、Workspace、Memory：放在一张桌上解释

你在会议里先问 Message List、Session、Workspace 的关系，又把 Workspace 说成 Context。这个困惑有根源：它们都“存着东西”，但存的是什么、模型何时能看见、关程序后是否还在，完全不同。

名字与白话存/组织什么什么时候用
Context · 本轮输入包本次发给模型的规则、消息、工具定义、必要记忆和运行状态。每一次请求模型之前组装。
Message List · 消息序列system/user/assistant/tool 等往来。作为本轮 Context 的一部分；也可以记录入会话。
Session · 一段连续交互的容器会话元数据、messages、runs、toolCalls、artifacts、summary。组织连续交互、隔离不同会话；实现保存/加载后才跨重启恢复。
Workspace · 受限工作区磁盘上的授权目录、文件、配置和产物；会议也用其存日志解释持久化。工具访问文件时，以及程序按设计加载配置/状态时。
Artifact · 任务产物生成的报告、文件、PPT 等。完成后交付、复读、继续处理；文件在磁盘不等于正文进模型。
Memory · 可再利用的信息近期信息、会话摘要、稳定偏好/事实/经验、工作区相关信息。需要时检索/选择，放入 Context；不是所有历史必经的压缩管道。

用今天、明天、另一件任务串起来

  1. 今天这次运行：程序在内存里保留工具往来，下一轮继续读，已经存在运行中状态。
  2. 程序关闭：如果没有保存会话，内存消息可能丢失；磁盘上生成的总结文件可能仍在，但不等于会话自动恢复。
  3. 明天回来：持久化意味着把必要记录保存到文件或数据库，再正确加载，接上对应会话。只写日志但不设计恢复读取，还不能声称能续上。
  4. 切到另一个会话：默认不能把旧会话历史串进来。若未来设计共享记忆，也必须明确选择和边界，而不是无差别混用。

持久化就是把需要保留的信息放到进程结束后仍在的存储里。会议用“把会话存成日志文件，下次再读”解释概念；总设计建议 SQLite 存会话、独立目录存 Artifact。前者是教学例子，后者是目标方案，不是相互排斥。

CLI 里有没有 Session？

命令行只是一种入口，不决定是否有会话。会议说“如果只理解成独立上下文窗口，肯定有”，又强调本项目当时没有多会话隔离和跨重启恢复。更稳妥的区分是：进程内连续消息与完整会话管理不是一回事。

会议的“没有状态、一次性的”应放回重启语境理解，不是说运行中的 Loop 连消息记录、计数和工具结果都没有。

两种 Context，也要分清

总设计的 RunContext 是程序执行时需要的会话、配置、权限和运行状态集合；模型的 Context 是本轮实际发送给模型的内容。前者不是要原封不动发给模型的包，密钥和内部权限对象不应该因为在运行环境里就进入模型输入。

Memory 的介入点不是“每说一句就自动记住”

总设计分短期会话上下文、会话摘要、长期偏好/事实/经验、工作区信息。会议金价演示先 Recall、结束后再考虑写回：前者查可能相关的旧信息，后者判断新信息是否值得保存。不相关时可以什么也不召回。

如果旧消息太长，摘要应保留任务目标、用户限制、已完成/进行中/未开始状态、失败原因和产物位置。压缩前后的下一步行动不能因关键事实被删掉而偏航。这里是对原设计“避免裁剪丢状态”的教学展开，具体算法、阈值与长期记忆治理不在工具切片中实现。

Provider 和 MCP 都像接头，为什么不是一回事？

Provider 接模型；MCP 接外部能力。它们都可以做格式转换，但位于主循环的两侧，解决的问题不同。

                         ┌─ Provider 适配层 ─ 模型服务 A / B
Agent Loop（任务总控） ──┤
                         └─ Tool Runtime ─ 内置工具
                                         └─ MCP 适配 ─ 外部 Server

上边：向模型发输入，接收回答或工具请求
下边：在授权下执行工具，得到真实结果后回填

先把 Provider 的两个意思拆开

会议有时用 provider 指供应商，例如提供模型服务的平台；项目里的 Provider Layer 指程序的模型适配层。它把内部统一格式转换成某家服务要求的格式，并把返回值转换回来。

会议假设同一模型通过不同供应商接入，可能一个接受 reasoning，一个称为 thinking，还有一个不支持推理强度参数；图片参数也可能不同。适配层隔离这些差异，使上层主循环不必为每家写一套逻辑。

统一格式不能创造缺失能力。供应商不支持某项能力时，要做能力声明、报错或明确降级，不能假装转换一个字段就支持了。

总设计目标包括统一消息、Tool Schema、ToolCall、流式事件、Usage、错误与超时/限流分类、重试/降级、能力与密钥配置。示意接口有 chat、stream、listModels、getCapabilities。第一版先适配一个云端服务，再验证第二个兼容服务或本地模型，不要求这次把供应商全接上。

会议出现的 DeepSeek、OpenRouter、GPT6、V4 Pro/Flash 等名称及参数例子，均按会议原始转写与假设保留，不作为当前型号、供应商能力或 API 规格。本册不联网核实这些例子，也不根据它们推荐模型采购。

MCP：把外部工具按共同协议接进来

会议中你问“每家 Agent 的 MCP 格式是否不一样”。其讨论要点是：MCP 本身是共同协议，不是各家随意定义一个互不相同的 MCP。具体客户端配置、支持的能力与版本仍需适配。

会议用“一个 GitHub MCP 里假设有 30 个工具”说明：接入以后，这些工具被发现、转换并注册为框架内部工具。30 是解释注册过程的示例数量，不是对某个当前插件的实测。

MCP Server（外部能力提供者）
→ MCP Client（本项目连接与发现）
→ Schema / 能力转换
→ 内部 Tool 或 Resource
→ 注册、权限与标准工具执行链

总设计不仅包含 Tools，也包含 Resources（资料）与 Prompts（提示模板）；还有 stdio/HTTP 连接、配置启停、断线、超时、进程退出、Server 信任等级、权限与日志。不能把“装上 MCP”教成“无须审查就授权一切”，也不能把所有 MCP 能力都当成执行工具。

工具层当前只为来源预留位置，不在三步切片里实现 MCP。先把内置工具的共同链路做明白，未来 MCP 工具才能复用它。

全项目还有什么？给工具层标一个清楚的位置

总设计不是只做读写工具。它希望形成一个可解释、可扩展、可演示的本地个人助手运行框架：从本地工作区理解任务，读取材料、调用命令等工具，生成报告/Artifact；以后支持会话恢复、Skill、MCP 与 Cron。后半部分是蓝图，不是本批全部交付。

模块实际工作与工具层怎样相接
Interaction Layer · 交互入口提交任务、展示回答/工具过程、确认权限、取消、管理会话和配置。传审批决定和取消指令，不在 UI 里写独立 Loop。
Agent Core · 总控组装本轮材料，调模型，识别最终回答/工具请求，管理运行状态、停止和完成验证。通过共同执行入口，不依赖具体工具类型。首版直接 Tool Calling / ReAct 式行动反馈循环，不先上复杂 Planner。
Provider Layer · 模型适配统一模型请求、响应、能力、流式、Usage 与错误。把内部工具说明交给模型，并识别模型返回的 ToolCall。
Tool Runtime · 工具受控运行注册、校验、权限、审批、执行、超时/取消、结果限制、错误与 Trace。本册主线，统一内置、用户、MCP 和 Skill 依赖工具的内部形态。
Session / Context / Memory / Storage组织会话，选择输入，保存信息和产物。保存调用与结果；提供本轮所需材料，不能串会话或把 Secret 发给模型。
MCP发现、转换、连接外部 Tools/Resources/Prompts。外部工具转换成内部 Tool 再走共同规则。
Skill · 方法包某类任务的方法、约束、提示词和依赖。指令进入 Context，依赖工具走同一执行链。Skill 不是 Tool 的别名。
Cron / Trigger · 启动来源按时间、CLI 或以后 Webhook 创建任务运行。复用同一个 AgentRun 与 Loop，不另造后台执行体系。
Security / Events / Observability约束访问、审批、凭据与敏感输出；记录状态与完整轨迹。贯穿每次模型/工具运行，不是最后补上的装饰。

Skill 要装什么，和工具差在哪？

总设计的方法包示意包括 SKILL.md（方法步骤）、manifest.json（名称、版本、触发、依赖）、可选 tools/prompts/scripts/references。系统需安装、发现、加载，判断启用时机，把指令加入 Context，检查运行环境/工具依赖、权限、版本。

用同一个任务看：Tool 是“读这份文件”；Skill 是“按什么步骤分析这类项目”；Agent 是配置了模型、提示词、工具和策略的执行主体。方法包可以引用工具，但不能凭它的文字绕过权限。

Cron 不是让模型自己一直醒着

计划触发 → 创建 Task/AgentRun → 创建或恢复 Session → 进入标准 Loop → 保存结果和 Artifact → 通知用户。一次性/周期任务、表达式、启停、并发、超时重试、历史和通知是后续 Scheduler 的工作；不必为了读一次文件先做定时调度。
