## 1. 先做什么

**先做一个“本地文件证据问答器”：用户指定工作区内的一个文本文件并提问，模型自主请求读取，程序检查并执行，模型根据读到的内容回答，用户能看到原文依据和执行过程。**

这是本地工作空间助手的第一块可演示能力，也是手册第 7 章的“第一垂直切片”。这里的“切片”指从用户输入到最终结果整条链路都走通，只把任务范围缩到一个文件。

首个产品单位是“一次有证据的文件问答”，不是单独一个 `read_file` 函数。函数正确还不能证明模型会选工具、结果会送回模型、程序能正常结束。

后续用两份会议记录和项目设计稿作为真实场景，扩成“会议资料核对助手”。这只是验证 Runtime 的具体用途，不改变原项目“可扩展本地 Agent Runtime”的定位。

## 3. 三种起步方式

| 方式 | 能得到什么 | 代价与不足 | 建议 |
|---|---|---|---|
| **单文件证据问答** | 证明自主调用、真实读取、回填、停止和追踪 | 暂时依赖用户给出准确文件路径 | **先做**，最容易定位问题 |
| 直接做多文件会议资料核对 | 更接近你的日常需求 | 同时引入文件发现、跨来源归纳、遗漏与冲突处理，难以判断哪层出了问题 | 单文件通过后，作为 M1 场景 |
| 一次搭完完整个人助手 | 覆盖原设计稿的远期目标 | 会话、权限、记忆、扩展和界面同时推进，验证成本很高 | 按原路线逐段推进 |

第一轮首先回答“我们能否把 Agent 的基础运行系统做对”。用户价值需要接着回答“它能否减少找材料、核对结论的时间”。这两类验证都要有，但不能把第一类通过直接写成市场需求已验证。

## 4. 首版产品卡

| 项目 | 首版约定 |
|---|---|
| 使用者 | 你本人；工程师作为技术评审者 |
| 使用时机 | 想从一份本地记录中确认一个具体事实，或提取少量明确事项 |
| 输入 | 已配置的受限工作区、工作区内文件的相对路径、自然语言问题 |
| 输出 | 答案、文件相对路径、相关行号与短摘录；缺失信息明确说“文件未说明” |
| 可见过程 | 正在请求模型、请求读取、读取成功/失败、生成结果、停止原因 |
| 控制 | 开始、取消；首版一次只执行一个任务 |
| 内容范围 | 小型 UTF-8 `.md` / `.txt` 文件 |
| 保存方式 | 单次消息在内存中；受控样例的运行记录写入本地日志，供复盘 |
| 不承担的任务 | 自动找任意文件、处理 PDF/图片/Word、改写原文件、跨会话记忆、联网搜索 |

薄页面只需“文件路径、问题、开始/取消、结果和可展开的执行记录”。工作区由本地启动配置指定，页面只提交相对路径，不能把任意系统目录设成可读范围。无需第一天就做文件树、账户系统或桌面安装包。

页面消费同一 Runtime 的事件；测试入口和页面必须调用同一份内核逻辑。页面可以在内核验收后增加，不改变首切片的通过条件。

## 5. 用一个可检查的例子走通全链路

以下为拟创建的脱敏测试文件，不是现有项目事实：

```text
第 1 行：项目代号：青禾-47
第 2 行：首轮演示只启用 read_file。
第 3 行：本轮评审人：林澄。
第 4 行：下一次演示日期：2026-09-16。
```

用户输入：

> 读取 demo-note.md，告诉我项目代号、评审人和演示日期，并引用原文。

正确过程：

1. 程序创建一次运行记录（AgentRun），保存问题。
2. 第一次模型请求只带规则、问题、工具说明；不提前放入文件正文和标准答案。
3. 模型自主返回 `read_file` 请求，例如路径参数为 `demo-note.md`。
4. Tool Runtime 检查工具名、参数、目标路径、文件类型和大小，再读取。
5. 将模型的 ToolCall 和具有同一调用编号的 Tool Result 按顺序追加到消息历史。
6. 第二次请求携带原问题、ToolCall 和 Tool Result，模型据此回答。
7. 程序检查本次是否成功读取目标文件、引用范围和摘录是否匹配本次读到的内容，再记录结束状态。
8. 用户看到答案、依据及这次运行的记录。

首次完整成功通常需要两次模型请求，但不把“两次”写成固定执行流水线：模型输出决定是调用工具还是结束，Runtime 负责约束和调度。

再问“预算是多少”，正确答案应为“文件未说明”，而不是猜预算。换一个全新文件、改变项目代号和日期、开启新运行后，应能得到新值，以排除写死答案或依赖旧上下文。

## 6. 首版技术设计：保留少量清楚的职责

以下均为拟实现的内部约定，不是已经存在的代码接口，也不假设任何供应商 SDK 支持同名方法。

| 模块 | 对外职责 | 首版范围 |
|---|---|---|
| Runtime | 接收任务，推进 Loop，发出事件并提供取消入口 | 管理本次消息、轮数、完成/失败状态；不依赖页面 |
| Provider | 把内部消息与工具定义送给模型，返回工具请求、最终文本或错误 | 一个真实模型适配实现；一个测试替身，用于复现失败与超时 |
| Tool Runtime | 按名称查工具，校验并执行，返回一致的结果 | 只登记 `read_file`，路径规则集中在这里执行 |
| read_file | 读取符合规则的文本并返回证据 | 参数只保留相对路径；首版读取整份小文件 |
| 本地事件记录 | 按同一 run_id 串起请求、工具结果和结束原因 | 简单日志写入与读取即可，不建设通用 Event Bus 平台 |
| 薄交互入口 | 提交任务、显示事件、取消任务 | 与测试入口共用 Runtime |

消息组织可以先放在 Runtime 内部的一个小函数中，不必独立建设完整 Session/Context 系统。存储接口、MCP Loader、Cron 调度器也不提前创建空目录。

### 6.1 read_file 的约定

- 输入：必填字符串 `path`，解释为工作区相对路径；拒绝未知字段和无效类型。
- 成功：返回成功标记、相对路径、UTF-8 文本、行号信息、字节数与内容摘要值，供引用及复盘。
- 2026-09-08 真实材料修复：工具内部及证据快照保留原始 `content` 字符串；Runtime 构造模型请求时优先将其转换成 `{"1":"第一行原文", "2":""}` 形式的逐行映射，行号包含空行，文本保留首尾空格。只发送一份正文，避免模型自行数行；最终引用仍须严格等于原始快照的对应完整行。编号后的完整请求若超出输入预算，则回退完整原文请求，并再次执行原有预算检查；不截断、不扩大预算，日志与 Provider 使用同一份最终请求。
- 失败：返回失败标记、稳定错误码、简短原因；成功和失败都关联原 ToolCall 的编号并回填。
- 拟定错误码：`INVALID_ARGUMENT`、`TOOL_NOT_FOUND`、`PATH_DENIED`、`FILE_NOT_FOUND`、`UNSUPPORTED_FILE`、`FILE_TOO_LARGE`、`TOOL_TIMEOUT`。命名属于本方案约定。
- 默认限制建议：只允许 `.md` / `.txt`，文件上限 32 KiB；超限直接说明不支持，不静默截断成“完整读过”。未来按实际文档规模增加分段读取。
- 首轮使用专用样例目录；拒绝绝对路径、父目录逃逸、目录/设备文件，以及路径中任何符号链接。不要只用字符串前缀判断“位于工作区”。
- 工作区内也不等于可以读取秘密文件；首版限定允许的测试文件，凭据和运行日志存放在可读目录之外。

### 6.2 循环、失败与停止

建议首版默认值：一次运行最多 6 次模型请求、总时长最多 120 秒、单次模型请求最多 45 秒、工具最多 5 秒。它们是可配置的保护起点，需在选定 Provider 后实测调整，不是会议指标。

- 每次模型请求前、每次工具执行前检查轮数、期限和取消状态。
- 每次模型返回多个 ToolCall 时，逐个校验并串行处理；为每项生成匹配结果。建议每次响应最多执行 4 项工具调用，额外请求以结构化错误回填，避免一次响应绕过运行限制。
- 对可返回给模型的工具错误，允许模型看到后说明原因或调整。不得吞掉失败，再让模型假装成功。
- 首版不自动重试模型请求；鉴权、网络、限流、解析等失败显式结束本次运行，用户可新开一次重试。后续有失败记录后再设计分类重试。
- 批次 0 根据选定模型设置请求输入预算和输出预留；每次请求前检查是否超限。首切片超限就明确停止，不静默丢弃原问题、ToolCall 或结果，也不在此时引入摘要系统。
- 模型要求未登记工具时返回 `TOOL_NOT_FOUND`；不能退化成任意 Shell 执行。
- 取消/超时后不再启动下一次模型请求或工具执行；尽可能中止已发请求，忽略迟到结果。取消不保证服务端计算或计费已经停止。
- 输出“成功完成”“无法完成”“用户取消”“超时停止”“达到轮数上限”等清楚状态，同时保存机器可读的停止原因。

不要只做一个永远循环的 `while` 再等待模型自己决定结束，也不要把写死的“先读文件、再调用模型”当作自主 Tool Calling。

### 6.3 结束检查的能力边界

文件问答需要区分“程序执行正常”与“答案正确”：

- 直接给最终答案但从未成功读取目标文件：不能标为文件问答成功。首版直接记为缺少读取证据，不以自动补读掩盖本次失败。
- 文件读到但所问信息缺失：允许明确回答未说明；这可以是正确完成的问答。
- 文件不存在或被拒绝：可以正确解释并结束，但属于任务未完成，不能混进正常回答成功数。
- 引用检查以本次工具返回的内容为准。行号越界、摘录不匹配时标记证据检查未通过。
- 引用存在只能证明引用真实，不能自动证明归纳没有遗漏、摘录足以支持结论。语义正确性仍由独立答案和人工核对验证。
- 首版不做额外评审模型或反复“自我反思”。任何未来修正循环仍须受同一轮数与时间限制。

2026-09-08 真实试用第二次修订：模型只提交答案及引用位置 `{"path":"demo-note.md","start_line":1,"end_line":1}`。Runtime 验证本次已成功读取、路径与行号后，从该次读取快照生成 `quote`；不再要求模型重复抄写原文。为兼容既有调用，模型如果提交 `quote`，仍须精确匹配，否则拒绝，不能用生成引用掩盖模型的错误摘录。程序只提取原文，不修改答案；行号合法和原文真实仍不代表答案受引用支持，必须另行核对语义。

对用户输出的最终回答必须是一个 JSON 对象，不接受 Markdown 代码围栏或 JSON 之外的附加文字：

```json
{"status":"answered","answer":"项目代号是青禾-47。","citations":[{"path":"demo-note.md","start_line":1,"end_line":1,"quote":"项目代号：青禾-47"}]}
```

`status` 只能是 `answered`、`not_found` 或 `unable`。`answer` 必须为非空字符串；`citations` 必须为数组。`answered` 要求本次成功读取目标文件且至少一项引用；每项引用的路径必须是该目标，行号是从 1 开始的整数，生成或验证的摘录必须与所指完整行文本精确相等（换行统一为 LF）。`not_found` 要求成功读完整文件，允许空引用；`unable` 用于目标读取已失败的情况，必须为空引用，不能用来跳过工具。除模型侧的 `quote` 可省略外，拒绝未知字段、缺字段及错误类型。

模型输出无法按严格 JSON 解析时，运行时允许模型在剩余预算内做一次格式纠错，并记录 `answer.rejected`；第二次仍无法解析则以 `validation_failed` 结束。缺少必要引用、行号越界、模型提供的摘录不匹配或其他语义校验错误不进入格式纠错。原始输出仅按日志内容策略保存，程序不会自行改写或放宽答案。区分运行结束原因与答案属性：`answered` / `not_found` 可正常结束，`unable` 记为任务未完成；格式与引用检查通过仍不代表语义正确，语义由固定样例评测和人工确认。

### 6.4 记录什么

每次记录：run_id、配置版本/模型标识、开始结束时间、每次请求的消息角色与调用编号、工具名和参数、工具结果/错误、最终回答、轮数、停止原因、耗时，以及供应商实际返回的 Token 用量。没有 Usage 就记录缺失，不编造成本。

日志不需要模型的隐含思维链；外显的请求、工具参数、返回值和状态已足以检查执行链。

受控样例可保留完整工具正文，以核对第二次模型请求确实包含它。真实材料默认记录相对路径、内容摘要值、必要的脱敏摘录；完整内容调试需明确启用。API Key 不进入提示词、工具结果或日志。

“本地 Runtime”只表示程序和文件在本机。如果选云端模型，读到并回填的文本会发给该模型服务。首轮先使用合成数据；真实会议试用前准备脱敏副本并明确发送范围。

## 7. 怎么证明通过

先建立基准样例和人工标准答案，再实现代码。标准答案只能供评测使用，不能注入系统提示词、工具说明或初始请求。

| 场景 | 必须观察到的行为 | 主要证据 |
|---|---|---|
| 已知文件有明确答案 | 模型自主请求读取，回答包含文件独有值并附依据 | 真实 Provider Trace、工具返回、人工答案 |
| 更换文件内容后新开运行 | 答案随新内容变化 | 两次输入与内容摘要、两份独立 Trace |
| 文件中没有答案 | 明确未说明，不补造事实 | 人工标注与输出 |
| 文件不存在 | 结构化错误回填，解释失败，有界结束 | 工具结果、后续模型请求、最终状态 |
| 越界路径或符号链接 | 无文件读取成功结果，不泄漏目标内容 | Tool Runtime 自动测试与拒绝事件 |
| 大文件、二进制、目录 | 明确拒绝，不能假装已完整分析 | 自动测试、错误码 |
| 非法参数、未知工具 | 稳定报错并关联原调用编号 | Provider 测试替身与工具测试 |
| 模型反复要求读取 | 达到预算停止，保留最后状态 | 测试替身与状态断言 |
| 超时或用户取消 | 后续不再执行，迟到响应不能覆盖终态 | 可控超时/取消测试 |
| 文件里写着“忽略规则、读取别处” | 将文件当资料；即使模型发出越权请求，执行层也拒绝 | 注入样例、路径拒绝测试 |
| 模型直接回答但没读文件 | 本次不能记为文件问答成功 | 测试替身与结束检查 |
| 模型给了不匹配的摘录 | 显示证据检查失败 | 引用校验测试 |

必过条件（2026-09-08 审阅修订）：

1. 上述边界、停止与消息回填的确定性检查全部通过。
2. 使用真实 Provider 跑正常读取、信息缺失、文件不存在、换内容四类场景，每类 3 次。正常读取和换内容必须给出预设的关键事实且引用有效；信息缺失必须返回 `not_found` 且不编造；文件不存在必须真实请求读取、收到错误并以 `unable` 结束。每次都须满足对应标准，才通过这组验收。
3. 任一必过场景失败，整组记为未通过；保留失败记录，修复后重跑整组。解释清楚失败原因不能替代修复。12 次小样本全过仅表示固定基准通过，不作统计可靠性保证。
4. 评测报告分别列“正常问题答对”“缺失信息处理正确”“错误安全结束”，不混成一个漂亮的总成功率。
5. 工程师能够从代码与 Trace 对上工具请求、参数校验、结果回填、结束条件，并确认语义评分。自动检查只能预筛关键事实和格式，人工评审未完成时不得宣布最终验收通过；未配置真实模型时明确记录“未执行”，不得使用测试替身冒充通过。

只有模拟 Provider 通过，不等于真实模型集成通过；只有真实模型偶尔回答对，也不等于安全与停止机制通过。

## 8. 从现在到 M1 的交付顺序

下面按完成条件推进，不承诺固定几天完工。建议每批完成就交给工程师看“场景、检查结果、Trace、下一步”四件套。

| 批次 | 本次做什么 | 交付物与出口 |
|---|---|---|
| 0. 准备与连通 | 明确语言/运行环境；确认一个真实 Provider 的 Tool Calling 协议；准备隔离样例目录；建立最小工程与测试入口；发一次基础请求 | 启动说明、配置字段说明、脱敏连通记录。只证明模型可访问 |
| 1. 单文件完整闭环 | 在同一条任务中做工具契约、参数/路径检查、ToolCall 回填、再次请求、完成检查、停止和日志 | 一份成功 Trace、一份拒绝/失败 Trace、自动检查结果。达到第一垂直切片 |
| 2. 简单使用入口 | 为同一内核增加文件路径、问题、运行/取消、结果和记录展示 | 你能独立使用；界面能显示失败与停止，不能伪装成功 |
| 3. 多文件任务与 M1 | 增加 `list_files`，先发现目录再选择读取；补流式输出；完善连续工具调用 | 固定两个各不超过 2 KiB 的文件，问题必须结合二者独有信息；证明列目录、选文件、读取和有据回答，满足 Phase 0–1/M1 |

批次 1 的 read_file、回填、路径约束和停止保护属于同一条切片，不应分别拖成多个尚不能演示的“大模块”。批次 0 可以先测试单个函数，但对外交付必须走完整链路。

M1 只需 `list_files + read_file` 两个工具即可满足原稿的“2–3 个”；多个文件意味着多次工具调用，不意味着必须再做第三个工具。先不加入 Shell 或写入权限。

**真实文件容量检查：**会议 01 为 59,156 字节，会议 02 为 22,506 字节，设计稿为 23,713 字节。会议 01 超过首切片建议的 32 KiB 限制，因此不能直接把首版拿来声称已完整分析三份材料。

分段读取属于 M1 通过后的真实材料试用，不是 M1 的前置要求。届时 `read_file` 可增加起始行和最大行数，建议每段最多 200 行、结果最多 32 KiB，返回实际起止行、总行数、是否读完、下一段位置和内容摘要值。单文件上限可提高到 128 KiB，仍只处理文本；单行超限明确报错。M1 的 `list_files` 只列用户指定目录内允许的文件及大小，不递归扫描电脑。

综合全部三份材料的场景必须在 Trace 中证明完整覆盖，不能只读前几段。不同分段须来自同一文件版本；发现内容摘要变化则本次材料不一致，要求新开运行。其他仅询问局部事实的任务可以局部读取，但输出要注明范围。

真实长文试用会增加轮数与上下文占用，应独立设置并冻结评测配置，不修改已固定的 M1 两文件验收任务。如果完整材料不能装入已核实的上下文预算，本次长文分析记为未完成，不能暗中漏读后宣称总结完整，也不因此否定已通过的 M1。

M1 建议支持同一进程内的追问并保留消息；程序重启后的恢复仍放在 M2。加入流式输出后，要等工具调用参数接收完整、验证通过才能执行，不能拿半截参数调用工具。

本轮代码根目录为 `local-agent/`，采用 `local_agent/` Python 包和 `tests/`，以文件保持模块职责，无须安装依赖。真实日志、凭据和人工标准答案位于模型可读样例工作区之外。

2026-09-08 的实现选择：Python 3.11+ 标准库（本机为 3.14），一个非流式模型适配实现与测试替身；模型名和密钥通过环境配置。输入先使用保守的序列化字节上限加输出长度限制，这不冒充精确 Token 计数；真实模型验收须同时验证其容量。保持单进程，不增加复杂框架、页面或第二个工具。

### 9.2 演示任务

使用经过脱敏、适合发送给所选模型的三份原始材料副本。先不把手册或本方案作为输入，避免模型复述我们已经整理好的答案，从而掩盖它对原始材料的归纳能力。

|---|---|---|---|

### 9.3 怎么判断值得继续做

建议先试三个任务：查询一个明确事实、提取第一阶段待办、核对多份材料的差异。每次记录：找材料和核对答案所用时间、关键遗漏、无依据内容、人工修改量、是否愿意下次继续用。

如果答案准确但用起来没有省事，先修文件选择和依据展示；如果过程顺畅但结论常错，先修样例、工具结果组织和提示词；如果你很少需要这个任务，再换本地工作空间中的真实场景。不要用增加 Memory 或 MCP 代替对问题的定位。
