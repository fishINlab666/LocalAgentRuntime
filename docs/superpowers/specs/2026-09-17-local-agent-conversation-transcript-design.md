# Local Agent 连续会话记录设计

## §0 状态与验证目标

2026-09-17：用户确认补齐 Codex 式多轮会话展示。本文件只解决网页的连续会话记录，不改 Agent Loop、会话持久化、模型 Context、工具、Skill 或 MCP 协议。

当前后端已经保存 Session、Run、用户消息、模型消息和工具结果；模型下一轮也能使用近期历史和摘要。页面却把历史 Run 渲染成按钮，点击后复用唯一回答区，因此同一时间只能看到一轮。当前要验证的假设是：**复用现有分页 Run 列表和单 Run 详情，就能让用户在中栏连续看到同一 Session 的多轮问答，同时保持右栏的单 Run 证据检查能力。**

完成条件：同一会话至少三轮用户问题和最终结果同时按时间可见；新 Run 原位追加并更新；刷新后恢复；更早记录可以续页且滚动位置不跳；切换会话不串内容；失败、取消和中断如实显示；现有引用、审批、产物、工具进度和迟到响应保护不回退。

## 1. 已确认的事实与缺口

- `messages` 已按 `session_seq` 持久保存用户、助手、工具和控制记录；不需要新增数据库表。
- `GET /api/sessions/{session_id}/runs` 已返回签名游标分页的 Run 摘要。
- `GET /api/sessions/{session_id}/runs/{run_id}` 已返回该 Run 的问题、状态、有效最终答案、消息、工具调用、审批、产物和 Context manifest。
- 当前 `renderRunHistory()` 只创建“状态 · 问题 · 时间”按钮；`openSessionRun()` 会清空并复用唯一 `#output`。这满足“旧 Run 可回看”，没有满足“多轮同时像聊天记录一样可见”。
- 模型使用的 `session_history` 是历史查询工具；用户看到的连续记录是前端展示能力，两者不能互相替代。

## 2. 方案选择

### 2.1 采用：现有接口＋前端懒加载详情

会话首次加载仍请求一页 Run 摘要。中栏按时间从旧到新生成每轮卡片，立即显示用户问题、状态和时间；最新 Run 自动读取详情，其他卡片在进入滚动视口或用户展开时读取详情，并在原位置显示最终答案。详情按 `session_id + run_id` 缓存，切换会话后丢弃不属于当前视图代次的返回。

优点是改动集中、无需迁移数据或改变后端权限接口；本机 loopback 上的少量详情请求足以验证真实体验。代价是首屏可能产生多个单 Run 请求，因此旧页采用按需加载而不是一次读取全部详情。

### 2.2 后置：分页 transcript 投影接口

未来若本机会话数量和单 Run 详情显著增大，可以增加一个只返回 `question + validated result.answer + state + time` 的分页投影接口，避免多个详情请求。当前没有性能证据支持先扩大后端接口，本批不做。

### 2.3 不采用：直接拼接原始 `messages[]`

原始消息包含工具协议、校验失败的模型尝试和程序控制记录。把它们全部当聊天文本展示，会把诊断数据误当最终回答，也会增加前端理解内部协议的成本。连续记录只使用用户提交和已验证最终结果；工具详情继续由右栏展示。

## 3. 页面信息结构

### 3.1 中栏时间线

`#session-history` 从 Run 导航列表变为会话时间线。每个 Run 对应一个稳定的 `article[data-run-id]`：

1. 用户消息：问题原文和提交时间始终可见。
2. Agent 区域：显示加载中、运行中、等待确认、已完成、失败、取消或中断。
3. 已完成且存在有效答案时，显示最终回答正文；不展示未通过验证的模型回复。
4. 引用数量、产物数量和工具步骤数量只显示摘要；完整内容在右栏。
5. 选中项用 `aria-current="true"` 标记，但不会隐藏其他轮次。

进入会话时滚动到最新一轮。用户主动向上滚动后，新状态更新不能抢走滚动位置；只有用户发送新问题时才滚动到刚追加的当前轮。

### 3.2 右栏仍检查单 Run

时间线负责连续阅读，右栏继续回答“这一轮发生了什么”。点击任一轮只更新当前 Run 的范围、引用、产物、审批历史、工具步骤和 Trace，不替换中栏时间线。运行中的审批卡仍保留在中栏当前轮附近，同时由右栏显示详细执行信息。

### 3.3 Composer

Composer 固定在中栏底部。发送后立即追加一轮用户消息和运行状态；轮询更新这张卡，不创建第二张重复卡。Enter 发送、Shift+Enter 换行、取消和输出目标规则保持现状。

## 4. 前端状态与数据流

前端在现有状态上增加并拆分以下内部状态：

- `historyRuns`：当前会话分页取得的 Run 摘要，内部按时间降序保留，渲染时按时间升序排列。
- `runDetails`：以 Run ID 为键的已加载详情和加载状态，只属于当前 Session 与 `viewGeneration`。
- `liveRunId/liveRunRevision`：当前唯一在途 Run 及其修订。轮询、审批、取消和运行控制始终绑定这里，用户查看旧轮不能改变它。
- `inspectedRunId/inspectionToken`：右栏当前检查的 Run 及选择代次。它只控制选中样式和检查内容，不承担执行权限。
- `detailRequests`：以 `sessionId + runId + viewGeneration` 为键的详情请求，负责去重和把乱序返回放回原卡。

`viewGeneration` 只在切换 Session、切换 Agent 或清空持久会话视图时递增；打开、展开或检查同一 Session 内的 Run 不得递增它。这样 Run 详情和续页可以并发，而跨会话旧返回仍会失效。`inspectionToken` 只淘汰旧的右栏选择结果，不影响其他卡片详情。

数据流：

1. 选择 Session，同时请求会话信息和第一页 Run 摘要。
2. 生成时间线骨架；读取最新 Run 详情。
3. 旧卡进入视口或被选择时读取详情；相同 Session、Run 和视图代次的在途请求去重。详情乱序返回时只更新自己的卡。
4. 点击“加载更早记录”使用现有签名游标，去重后向时间线顶部追加，并通过加载前后的锚点位置保持视口。
5. 新提交创建 Run 后设置 `liveRunId`，追加摘要和详情占位；轮询只更新对应卡片。用户检查其他旧轮时，当前 Run 的审批和取消仍保持绑定。
6. 点击某轮设置 `inspectedRunId` 并递增 `inspectionToken`；右栏只接受该选择代次的结果，不停止 `liveRunId` 的轮询。
7. 切换 Session/Agent 时递增 `viewGeneration`，清空详情缓存、在途索引和观察器；旧请求晚到直接丢弃。

详情加载失败只影响该卡：显示“暂时无法载入这轮，重新加载”，不会删除摘要、切换会话或自动重提任务。终态 Run 的历史审批只读；刷新页面不得再次 POST、执行工具或恢复旧审批能力。

## 5. 安全、性能与可访问性

- 动态问题、回答、状态和来源继续使用 `textContent`，不渲染模型 HTML。
- 只展示后端已经验证并放入 `result.answer` 的最终回答；原始工具消息不进入普通聊天正文。
- 首页保持现有 20 个 Run 上限，详情按需读取；不一次加载完整数据库历史。
- “加载更早记录”按钮保留键盘操作；每轮使用语义化 `article`，用户/Agent 标签可被读屏识别。
- 当前轮、运行中、失败和选中状态不能只靠颜色区分。
- 桌面中栏和移动端单栏都使用同一时间线；手机抽屉行为与 44px 触控目标不变。

## 6. 验收标准

浏览器固定验收必须覆盖：

1. 同一持久 Session 的三轮问题和三轮回答同时存在，顺序从旧到新。
2. 点击旧轮后，右栏切到对应引用/产物/步骤，中栏其他轮次仍在。
3. 新提交只追加一个用户卡，完成后在同一卡中出现答案。
4. 刷新后仍显示三轮；不产生新的 POST、Provider 调用、审批或工具执行。
5. 21 个以上 Run 先显示第一页；加载更早记录后向顶部追加，ID 不重复且可视锚点基本不变。
6. 详情请求失败可以单卡重试；失败、取消、中断和等待审批状态均不显示为成功。
7. 两张旧卡详情乱序返回时各自进入原卡，期间 Run 续页不失效；A/B Session 快速切换后，A 的迟到详情不得进入 B。
8. 新 Run 等待审批时可以检查旧轮；旧轮进入右栏，但批准、拒绝和取消仍只能作用于当前新 Run。
9. 切换 Agent 不能跨归属显示；390px、1024px 和 1440px 下 Composer 可见、时间线可滚动、无页面级横向溢出。
10. 既有 Agent/Session 分页、Enter 发送、审批、引用、产物、Skill/MCP 管理和 XSS 回归继续通过。

本批使用合成 HTTP/浏览器夹具验证展示和竞态，不需要真实 DeepSeek 调用。达到上述条件后收口；流式 token、跨会话 Memory、批量 transcript 后端接口和新的消息编辑能力继续后置。
