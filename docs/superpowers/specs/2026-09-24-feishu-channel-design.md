## 3. 接入方案选择与首批范围

采用 **企业自建应用机器人 + 官方 Python SDK WebSocket 长连接 + 同机工作台**。本机主动连接飞书，适配本地使用；不向公网暴露现在的 loopback HTTP 服务。SDK 只承担消息传输与平台协议，任务仍由现有工程执行。

替代方案：

1. 公网 HTTPS Webhook：适合长期服务器部署，但需要公网入口、验签、防重放和运维；本批不选。
2. 飞书卡片直接审批与云端文件访问：适合手机，但需要额外用户认证、卡片回调和远程产物授权；与已确认的同机范围不符。

首批包含：文字私聊、显式绑定既有 Session、普通资料任务及显式历史追问、状态查询、显式取消、只读通知、收件/发件持久化、网页定位与在途 Run 接管、固定验收与日志。

后续批次：飞书附件自动下载和受管导入、云文档与表格连接、群聊、手机远程访问、卡片审批、另外三个业务模板。首批遇到附件或富文本必须明确返回“不支持此输入，请先在工作台导入资料”，不丢弃附件后擅自启动残缺任务。引用消息正文或附件不能扩大绑定范围。

首批沿用工作台已有 `.md/.txt` 与受管文字 PDF/DOCX 能力；不把“经营表”误写成已有 Excel/CSV 解析与确定性计算工具。

## 4. 用户路径和消息语义

### 4.1 绑定一次，后续复用

1. 用户在本机工作台创建/选择一个持久 Session，固定 Agent 修订和资料范围。绑定仅支持已存在的、当前服务可访问的 Session。
2. 在本机渠道配置中明确填入应用、租户、本人 `open_id` 和目标私聊 `chat_id`，选择上述 Session；保存前显示范围。非密钥 ID 可由应用后台测试信息获取，启动帮助给出定位方法。App Secret 和模型 Key 只经环境变量，不写进绑定 JSON、数据库或聊天。
3. 未配置的主体不得自动成为主人；不采用“第一个发消息的人自动绑定”。未授权消息只记录拒绝计数，不启动任务、不向其泄露任何工作区信息。
4. 绑定键至少含 `channel/app_id/tenant_key/open_id/chat_id`，目标含 `agent_id/session_id/binding_revision/enabled`。会话范围继续以现有 Session 为权威，不另造一个只靠提示词生效的 `allowed_scopes`。
5. 改绑使用新 revision；未派发旧事件变为失效，不能被改投新资料范围。停用取消该绑定的在途 Run，并停止其未发送通知；已产生的文件保留。

初版可用本机配置文件与 CLI 管理绑定，不强制先做一套配置 UI。接收者、资料范围以及写入规则必须可在本机核对。

### 4.2 输入规则

- 普通文字：作为资料问题提交到固定 Session。
- `/记录 <问题>`：显式 `task_type=conversation`，复用已有会话历史工具；不由分类模型猜测任务类型。
- `/报告 <相对路径>` 换行后跟问题：显式声明本 Run 的唯一输出路径，再提交资料任务。例如路径可为 `gzsz-brief-20260924.md`；父目录需存在。路径缺失/非法或正文为空时在入口拒绝，不调用模型。
- `/状态` 或 `/状态 <run_id>`：返回该绑定的最新/指定 Run 状态及工作台定位链接。
- `/取消 <run_id>`：仅能取消该绑定创建且仍在执行的 Run；终态重复取消只回状态。取消正在调用的模型时，沿用已有 Provider 超时和 Runtime 检查点，不声称能撤回已发出的网络请求。
- “同意”“确认写入”只是普通文本，永不调用审批接口；有待审批任务时返回本机审批提示，不创建新任务。
- 未知斜杠命令只回帮助；机器人自身消息、群聊以及不匹配应用/租户/用户/私聊的消息不创建 Run。

同一时刻沿用一个活跃 Run。新任务遇忙直接记录 `rejected_busy` 并明确回执，用户结束当前任务后另发一条；首版不排无限任务队列。同一被拒消息重投仍然被拒，不能过几分钟突然执行。状态和取消命令不受模型忙状态阻塞。

**消息撤回与任务取消分别定义。** 首批保证 `/取消` 和网页取消；飞书撤回原消息不自动撤销已受理任务，不删除文件。帮助中明确提示，离线验收检查此行为。SDK 中确有撤回事件模型，但撤回者授权、乱序及平台订阅需要另做接入；本批不宣称已经支持“撤回即取消”。这一首批范围已获用户确认。

### 4.3 用户看到的结果

固定通知节点为已收到（等待启动）、执行中、待本机确认、终态；“已收到”只说明收件已落库，不表示 Run 已启动。忙时另回明确拒绝。通知可以合并已过时的中间进度，避免终态之后又收到“正在运行”。这些是状态摘要，不是模型自由生成的经营结论。

默认通知只含不敏感的状态、Run 短编号、资料/产物数量和工作台定位链接；不回显原问题、原文、人员数据、绝对路径、完整答案或报告正文。数据不会因为位于私聊就默认可以复制到飞书。

## 5. 最小架构与执行接点

```text
飞书私聊事件
  → 官方 SDK 传输适配
  → 主体/绑定/格式校验 + 持久 inbox
  → ChannelTrigger → 已有 WebRuns / SessionService
  → 原 Runtime → Tool / Provider / Skill / MCP
  → 原 Approval / Artifact / Trace
  → 状态投影与持久 outbox → 固定私聊通知
                     ↘ 本机工作台查看、批准、取消、下载
```

新增 `ChannelTrigger` 是本批拟建契约，不冒充已有接口。包含规范化渠道、消息 ID、事件 ID、绑定 ID/revision、可信主体、Session、任务类型、问题、显式输出路径和稳定 `client_request_id`。它不携带工具授权，也不自动把原始飞书信封塞进模型上下文。

首批在现有服务启动器增加可选飞书模式，共享**一个 WebRuns 实例、一个 SessionStore 和一套在途控制**。不要为了命名整洁搬迁整个 WebRuns，也不要单开第二套 SessionService.execute 流程。入站工作者调用现有执行接口，适配层调用前必须先完成主体/绑定校验；内部调用不依赖伪造浏览器 Header。

官方 SDK 的回调只做限定校验与持久入站，不同步等待模型、审批或飞书发送。工程目标为本地轻量回调 1 秒内完成；这是本项目预算，不当作本次已核实的平台 SLA。落库失败不得成功 ACK；已落库再响应才允许后台派发。SDK 收件线程、工作者和 HTTP 线程的生命周期归同一启动器管理，启动失败/退出时关闭通道和在途 Run，释放数据库线程连接。

实施首先验证选定发行版 SDK 的启动、ACK、重连与退出路径，固定依赖版本；不得直接追随 `v2_main` 动态分支，也不引入另一套 Agent framework。实施已固定并安装 `lark-oapi==1.7.3`，SDK 构建器及 ACK 已离线核对；真实账号连接仍待验收。SDK 无公开停止接口，使用可终止传输子进程；Runtime 仍只在原主进程执行。

## 6. 收件、幂等和恢复

沿现有 State Store 增量迁移至下一个 schema，复用迁移前备份与版本拒绝，增加三类表：

| 表 | 必要字段与约束 |
|---|---|
| `channel_bindings` | 主体五元组、Session/Agent、revision、enabled；同一主体私聊只允许一个有效绑定 |
| `channel_events` | 内部 event key、平台 event_id/message_id、类型、绑定快照、规范化请求、确定性 request ID、Run ID、状态、收件/派发时间、有限错误码；消息幂等键唯一 |
| `channel_outbox` | event key/可空 Run ID、通知种类、绑定与目标快照、固定正文、稳定 uuid、状态、attempts、next_attempt_at、飞书 message_id、时间和错误码；同事件同通知节点唯一，关联 Run 后另约束同 Run 同生命周期节点唯一 |

不创建第二张 `approval_token` 表；继续用原 approvals 和文件发布证明。事件表以外键/受控关联连接既有 `runs`，不假装数据库里存在 `agent_run` 或 `artifact` 这些单数表。渠道数据进入既有数据库备份路径并验证恢复，目录和数据库沿用私有权限。

两层防重：

1. 入站业务键使用 `feishu + app_id + tenant_key + event_type + message_id`；消息正文完全相同但 message_id 不同，是新请求。平台 event_id 在同渠道、应用、租户及事件类型内作为辅助唯一关联与审计字段；同 ID 不同主体/内容冲突时拒绝，不覆盖原记录。
2. 派发使用上述键生成固定长度 `client_request_id`。复用 `(session_id, client_request_id)` 唯一约束与请求指纹。哈希用于编码稳定标识，不用于对消息正文去重。

收件提交即冻结 Session、绑定 revision、请求与输出路径。保存与“已收到” outbox 同事务；事务提交前不能通知已收到。单一派发工作者在共享运行锁内完成再次校验、忙状态检查与 Run 提交，仍由既有程序约束并发。

事件状态：`received → dispatching → dispatched`，或 `rejected/invalidated/interrupted_before_dispatch`；执行结果从关联 Run 读取，不把通知失败写成 Run 失败。

宕机窗口必须分别验收：

- 事件尚未持久化：回调失败，由平台重投；不虚报受理。
- 事件已持久化但没有 Run：启动恢复时保守标为 `interrupted_before_dispatch`，通知用户重新发起；不在重启后悄悄执行旧写入请求。
- Run 已持久化但事件尚未写回 Run ID：按冻结的 Session + request ID 找回并关联；已有 Run 走原恢复逻辑，不再调用模型。
- 已写出文件/已有发布意图：只读取既有恢复与 Artifact 状态；未知写入结果如实标未知，不删除、不重写、不伪造成功。
- Run 已终态但 outbox 尚未生成：按 Run 终态、审批/Artifact 记录补齐缺失通知，唯一约束防止重复创建。

如用户通过工作台“继续中断 Run”，继续得到新的 Run 与新审批；渠道只对同一绑定下显式继续的父子关系建立新映射。原消息重投只指向原 Run。绑定失效时不自动把子 Run 发给旧收件人。

## 7. 通知重试与权限

`run_state` 和 `delivery_state` 分开查询。`delivery_state` 至少区分 `pending/sending/retry_wait/accepted/unknown/failed/suppressed`。

- API 明确成功并返回飞书 message_id 后才记 `accepted`，含义是平台接收，不等于用户已读。
- 明确未接收的错误可有界重试：最多三次，退避并遵从服务端限流；只重新发送同一 outbox，绝不重新提交 Run。
- 网络超时、发出后断网、发送成功但落库前宕机，均可能是“已送到但本机不知道”。标 `unknown` 并在工作台显示，不无上限盲重发。
- 固定通知 uuid 使用官方发送消息模型已有字段；本次未核实其服务端去重时窗，不依赖它承诺永久恰好一次。未知通知允许用户显式补发，仍使用原 uuid，说明可能收到重复通知；任务和文件不会重做。
- 终态抑制尚未发送的过时进度或审批提醒；停用/改绑检查在每次发送前执行。目标只从绑定快照取，不从模型答案或正文里的收件人取。

首次接通仅需所选自建应用的机器人、本人单聊收件和机器人发消息能力。准确权限 ID、发布/可见范围与订阅项必须在真实准备阶段核对；不申请群全量消息、通讯录全量、云盘遍历或企业经营系统权限。

飞书 ACK 与面向用户的“已收到”消息是两件事：前者是传输回执，后者必须有台账证据。飞书通知的固定模板属于本渠道预先授权的回复动作；模型无发送工具，不能自由指定外部目标或全文。

## 8. 工作台接管与本机授权边界

拟新增定位形式：`http://127.0.0.1:<当前端口>/#agent=<id>&session=<id>&run=<id>`。这是待实现格式；片段中只有定位 ID，无 API Key、进程令牌、正文、路径或授权能力。

页面从正式 HTTP 启动入口加载资源与进程令牌，校验 Agent/Session/Run 关联后再定位。不可见目标给出错误，不回退到另一会话并误以为是目标结果。链接需要飞书桌面客户端打开本机浏览器；真实试验中验证可点击性，若被客户端阻止，提供复制地址的明确兜底，不计作一键访问已通过。

补齐两个现有 UI 接点：

1. 页面载入/切换 Session 时发现 `queued/running/waiting_approval`，调用同一详情接口接管 `liveRunId`、轮询、取消和当前审批；只恢复观察，不 POST 新任务。
2. 页面停留时通过有界摘要轮询或明确刷新发现同 Session 的外部新 Run；浏览器后台降低频率；Session 切换的旧响应仍失效。审批按钮始终绑定 live Run，历史检查仍使用 inspected Run。

审批动作沿用原 Broker 对 Run、目标、冻结参数与内容摘要、有效期和一次性消费的校验。来源飞书主体写入渠道关联；实际批准者是本机可信浏览器操作者。**此边界不证明浏览器操作者经过飞书 OAuth 身份核验**。本机其他具有访问权限的用户是信任前提，不能把这个模式推广为多人共享主机授权。

转发飞书链接和“同意”文字本身不授予远程访问或执行能力。手机和其他电脑上的 loopback 指向它们自己，第一版不支持；不通过关闭 Host/Origin/令牌检查来解决。

产物下载继续经现有认证接口，核对 Session/Run/Artifact 关系、文件 SHA-256 和发布回执；链接不直接暴露文件系统路径。文件已生成但最终回答失败或任务被取消，分别显示已生成产物与任务结果，不把二者混为一谈。

## 9. 业务样例与真实价值验证

首例：**KA 广深会前一页诊断提纲**。产出分为营业供给、自然/商业流量、进店下单、首屏套餐四层，另列两城差异与待问项；动作优先级、费率、资源预算由用户决定。

现有默认预算最多四次工具调用。为避免第一次接入同时改工具预算，首个链路样例将四类业务输入保留来源标签，组织为两份小 Markdown：①同周期门店周报及营业/供给记录；②套餐权益及上次行动纪要。每份不超过 8 KiB；目录仅此两份输入，输出写入预先存在的独立目录。预算可以覆盖 `list_files + read_file ×2 + write_file`，模型仍自己选择工具，不预塞正文。若模型用完预算无法完成，记录失败，不能临时无限放宽。

样例刻意包含费率缺失、一条过期纪要、两城不同经营状态。期望不是唯一措辞，而是所有数字、专名与判断可定位；不同周期不能强算环比，缺失不补造，原因只能列候选。不额外新增业务 Skill 安装作为 IM 验收前置。

四个场景映射：

| 场景 | Agent 工作 | 人的决定 | 后续资料缺口 |
|---|---|---|---|
| 广深诊断，首批 | 对齐周期、四层排查、引用与待问项 | 经营动作、门店例外与资源优先级 | 可授权真实周报和纪要 |
| 分层召回 | 对齐分层、历史动作和活动日历 | 权益力度、预算和触达 | 实际分层口径、动作/效果记录，不读个人级 CRM 数据 |
| CNY 排品 | 并列当时判断与实际结果、主次推和清尾草稿 | 价格带、备货和主推结构 | 当时决策记录与真实结果，不能倒推历史依据 |
| 品类日坑位 | 可比口径对齐、排序、异常候选 | 原因判断与下一场调整 | 同口径坑位底表；确定性计算若超出现有能力须单独开发 |

不承诺后三项只是改配置就一定完成，真实表格接入、计算、资料量和口径可能需要新能力。

效用评测使用同一包获准资料、同一交付要求，比对手动与 IM 路径：主动插手次数、事实/结构修改次数、从提出到可用的墙钟时间；首次配置耗时单列，不藏在统计之外。同步记录来源覆盖、事实错误与“误把正常波动当异常”的例子。首个对照仅为个案；以后连续任务采样才形成稳定结果口径，不编造百分比提升。

## 10. 固定验收与证据

### 10.1 离线工程验收

| 编号 | 必过场景 | 必须取得的证据 |
|---|---|---|
| F1 | 正常文字→Session→工具→答案/产物 | 事件键关联一个 Run；初始 context 无正文；真实文件读取与工具回填 ID；Artifact 与审批内容一致 |
| F2 | 同一消息重复投递、并发投递、不同 event_id 同 message_id | 只有一个 Run/初始用户消息；最多一次成功写入；无新增模型请求 |
| F3 | 不同 message_id 的相同文字 | 非忙时分别生成两个 Run；不按正文吞消息；忙时明确拒绝并保留拒绝状态 |
| F4 | 错应用/租户/用户/群聊/机器人、改绑与停用 | 不启动未授权任务、不发送敏感回复；资料根范围不变 |
| F5 | 飞书发起后打开/刷新工作台 | 正确 Session/Run、待审批完整内容和取消可用；刷新不重提任务 |
| F6 | 历史 Run 与 live Run 来回切换 | 审批/取消不会作用于旧 Run，过期/重放审批不能写入 |
| F7 | 各宕机窗口 | 台账与 Run 能对应；未派发保守中断；已执行不重做；未知发布如实展示 |
| F8 | 文件已写、通知失败/超时/断电 | 文件和 Run 数不增加；投递状态为 retry_wait/unknown/failed，恢复只处理通知 |
| F9 | 取消、审批拒绝、审批到期、模型超时 | 明确停止原因、无未批准写入；取消不删除已完成产物 |
| F10 | 原飞书消息撤回、附件、未知命令 | 行为与 §4.2 一致；不谎报撤回已取消、不无视附件启动残缺任务 |
| F11 | 越权深链接、文件修改、恶意文本 | 原认证和关联校验拒绝；哈希不符不下载；正文不执行 HTML/脚本 |
| F12 | SDK 重连/退出、数据库迁移和备份恢复 | 单一执行管理器；旧会话仍可读；来源台账恢复；无后台任务失控 |

重放、故障注入、合成 SDK 和脚本模型必须分别标识，不能标为真实平台事件或真实 DeepSeek 通过。先跑相关定向组，只在最终里程碑跑一次完整受影响回归，不因每个小修复重复全套。

### 10.2 真实接通验收

从 README 将新增的正式飞书启动入口启动服务，在真实浏览器打开服务实际输出的地址，检查 HTML/CSS/JS、首屏、目标 Session、发起/审批/产物主路径。fixture 通过不能替代该检查。

固定真实组最多 **2 个模型 Run、合计 20 次 DeepSeek 请求**：一个广深诊断报告闭环；一个明确取消路径。预算含失败尝试，不自动追加；同一问题最多定位一次、修复后定向复测，若总预算耗尽则报告未通过并等待新的授权。状态查询、幂等重放、通知补发不产生模型费用。

真实组使用明确标识的样例包；获准真实经营资料另行做效用评测。取得真实飞书接收消息 ID、通知 API message_id、Run ID、原始 JSONL/SQLite 记录、产物 SHA-256，核对消息→工具实际执行→下一轮 context→结果→飞书通知的完整链路。单次真实成功证明闭环，不证明所有异常都由飞书平台真实触发过。

应用配置、凭据与发布权限尚未提供。实现阶段可完成离线开发，真实验证需要用户在本机配置环境变量并确认应用可见范围；不扫描其他终端/凭据存储。用户尚未批准自动将经营原件上传飞书，本设计默认不上传。

### 10.3 日志契约

渠道日志记录白名单事件：received/rejected/duplicate/dispatched、Run 生命周期、通知尝试与平台确认。字段为规范化来源标识、绑定 revision、Session/Run 关联、状态、耗时、错误码和计数；模型 Trace 继续使用原格式。

不得把 SDK DEBUG 原始消息、HTTP Header、App Secret、访问令牌、WebSocket 完整连接 URL、原始经营正文写进后台日志。SDK 默认 INFO 也可能输出连接 URL，需配置过滤或降级并验证。持久化执行所需问题和绑定保存在私有 SQLite，区别于可分享诊断日志。验收导出的事件 ID 可在本机保留，公开材料使用脱敏关联号；不自动提交 raw trace。

## 12. 设计压力检查与决策

这是**设计 Gate**，不运行应用或模型。退出条件是核心数据流、失败恢复、职责和验收可对应到实现接点，平台未知项被明确隔离为预检事项。

| 判定项 | 技术证据 / 压力输入 | 大白话 | 决策影响与责任 |
|---|---|---|---|
| 重复与合法再发 | Session 内唯一键存在，但缺渠道台账；重放同消息与同文新消息 | 可以防止重复下单，又不吞掉用户真正的新任务 | 设计通过；开发者按 F2/F3 验证后才能声称实现 |
| 重启断点 | WebRuns 初始化会恢复未终态 Run | 另开 Bot 执行器可能把原任务误判中断 | 设计通过；复用单管理器，开发者必须验证 F7/F12 |
| 审批与结果访问 | 当前页面不接管外部 Run，下载需认证 Header | 只接收消息还不够，必须能打开正确任务并批准 | 设计通过；深链接与活跃 Run 接管属于首批必做 |
| 任务/通知分离 | Run 终态与网络发送可在不同时间失败 | 文件做好了但通知没到，只补通知 | 设计通过；允许通知 unknown，不允许虚报已读或重做任务 |
| 用户范围 | 已选择同机；原网页无飞书 OAuth | 本机模式可用，但不等于手机/多人权限完成 | 用户已确认首批范围；远程能力后置 |
| 四场景价值 | 求职审计说明现有演练为虚构输入/人工样稿 | 现在能测工程链路，不能凭这些资料说经营提效 | 用户提供获准资料后做单独效用评测；助手不编指标 |
| SDK/平台语义 | 官方 SDK 有 ws、事件与 uuid 字段；动态文档正文未读到，发行版未固定 | 技术路径有依据，具体权限、时限和去重窗口还没实测 | 实施第 1 步先验证；不得把这些参数写成平台已保证 |

**技术交接：设计范围核对 PASS，产品交付尚未验收。** 原参考方案若直接按“接口全有、四张表即可”实施会漏掉执行衔接、宕机对账与网页审批接管；本草案已定义修正方案。用户已确认首批文字输入/本机审批/显式取消边界；开发者按[实施计划](../plans/2026-09-24-feishu-channel.md)落地。本段保留设计 Gate 结论；后续实现与 F 项离线证据见[验收记录](../../../local-agent/trial/feishu-check.md)，真实组尚未执行。
