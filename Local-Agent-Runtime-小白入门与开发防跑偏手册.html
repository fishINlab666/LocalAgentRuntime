01 · 约 8 分钟

这个项目究竟要做什么

本章问题：为什么“会聊天”远远不等于做出了这个项目？

一句话结论

Local Agent Runtime 是模型外部的一套运行系统：它让模型能在个人电脑上持续接收任务、选择工具、执行真实动作、保存过程、处理权限与错误，直到形成可检查的回答或 Artifact。

项目的正式定位

设计文档把它定位为“个人本地智能助手框架”，主要运行在个人电脑。用户可以通过 CLI 或桌面界面交流；Agent 可以调用本地或外部工具，管理连续会话，并通过 MCP、Skill、Cron 扩展能力。它同时是一件求职作品：不仅能演示，还要让面试官看见工程闭环、边界、安全与演进路径。

贯穿项目的演示场景

  1. 用户要求 Agent 分析一个本地项目。
  2. Agent 查看目录和文件，必要时执行命令。
  3. 经历多轮 Tool Call 后，生成报告或修改建议。
  4. 会话、模型调用、工具轨迹与产物被保存。
  5. 程序重启后，用户能恢复并继续任务。
  6. 后续用 Skill 增加工作流，用 MCP 接第三方工具，用 Cron 定期检查。

内核和外壳不是一回事

会议 01 反复强调：对话框、CLI、工作流节点、传统表单都只是上层产品形态；真正决定智能效果的是底层内核能否基于可信数据完成有效分析。企业交付时，要先理解行业、业务场景、现有生态和工作流程，再决定把能力包装成什么样。不能因为市面上常见对话入口，就误以为 Agent 产品必然长成聊天窗口。

设计文档的首版建议

Interaction Layer 第一版建议只做 CLI，核心稳定后再增加桌面界面。

会议中明确出现的用户偏好

用户不偏好 CLI；会议也接受内核完成后包一层简单页面。

教学解释：怎样不让差异阻塞开工

第一垂直切片先用最薄的脚本、测试或调试入口验证内核；是否补 CLI 或简单页面，是后续演示选择，不应抢在 Loop 前面。

当前项目必须能展示的能力

  • 完整 Agent Loop，而非单轮聊天封装。
  • 统一 Tool Runtime，让模型安全操作外部环境。
  • Provider 层屏蔽云端或本地模型差异。
  • Session、Context、运行状态和长期记忆管理。
  • MCP、Skill、Cron 的统一扩展与触发机制。
  • 模型调用、工具执行、异常、Token 和成本可观测。
  • 本地文件、Shell、网络和删除操作具有权限边界。

常见误区

先做一个漂亮聊天页面，再把 API 接进去。这只能证明“界面能请求模型”，不能证明工具闭环、状态、安全、恢复和可观测性成立。

02 · 约 8 分钟

从大模型到 Agent：多出来的到底是什么

本章问题：为什么一个能生成文本的模型，还需要 Runtime 才能成为可工作的 Agent？

一句话结论

模型本体接收输入、生成输出；Agent 系统在它外面补上实时信息、状态连续性和真实行动能力。

先把模型看成一个“输入 → 输出”的函数

会议 01 从生成式 AI 的本质讲起：模型基于训练阶段学到的模式，对输入生成文本或其他多模态输出。对工程入门来说，先把它理解为一次 API 调用最有用——本次请求给它什么，它本次就看见什么；它不会因为你上一次调用过，就天然记住上一次内容。

会议归纳的三个局限

01 数据不实时

训练数据有时间边界。需要 Web Search 或业务数据工具，把新信息取回来。

02 没有天然状态与记忆

独立 API 请求互不相识。应用必须把历史消息重新放入下一次 Context。

03 不能亲自做事

模型只能生成输出；真正读文件、运行命令或写报告的是 Runtime 中的工具执行代码。

Agent 不是一个更神秘的模型

在本项目中，Agent 描述的是模型、提示词、工具和策略的组合；一次具体任务叫 AgentRun。模型仍然只输出文本或 ToolCall 参数。Runtime 解析输出、执行工具、把结果写回，再询问模型下一步。所谓“自主”，来自这个受控循环，不是模型突然拥有了电脑权限。

教学解释

类比：模型像只负责判断与写指令的“大脑”，Tool 是可调用的动作，Context 是桌面上摊开的全部材料，Runtime 是按规则递送材料、执行动作、记录过程并踩刹车的运行系统。类比只帮助分工，不意味着模型真的拥有人的意识。

常见误区

把“模型能力强”直接等同于“Agent 工程可靠”。模型会影响判断质量，但工具参数校验、权限、重试、状态、停止条件和 Trace 都是外部工程责任。

开发检查点

看到任何“Agent 能做 X”的需求，都拆成三问：模型需要看见什么？它要请求哪个原子动作？Runtime 怎样安全执行并把证据送回去？

自检：模型本体没有哪三样东西？
  1. 为什么第二次 API 调用不会天然知道第一次聊了什么？
  2. Web Search 解决的是哪一类局限？
  3. 本地文件真正由谁读取：模型还是工具代码？

03 · 约 9 分钟

Context：模型这一轮实际看见的全部材料

本章问题：无状态 API 为什么能表现得像“记得前文”？

一句话结论

不是模型在后台偷偷记住你，而是应用在每轮调用前重新组装 Context。

从单个 Input 扩展成 Context

会议 01 先用两轮对话解释：第一轮问某人的新闻，第二轮只问“他今年多大”，如果第二次只发送这一句，模型不知道“他”是谁；若把第一轮 User、Assistant 和第二轮 User 依序放进 Message List，模型就能从本次请求里解析指代。

Agent 配置与 Skill 指令当前运行方式
会话摘要与长期记忆被筛选、压缩后重新注入
Message ListUser / Assistant / Tool 的近期历史
当前 Run 状态目标、进度、待处理事项

每一部分回答一个不同问题

Context 组成与作用
组成回答的问题漏掉后的表现
System Prompt“你是谁、要遵守什么”身份、边界和输出行为漂移
Message List“刚才发生了什么”多轮对话断裂

Context 不是数据库，也不是 Session

Context 是某一轮请求实际送给模型的集合；Session 是保存连续交互、运行、工具调用、Artifact 和摘要的容器；Memory 是被保存、加工、检索，并在需要时重新放进 Context 的信息。数据库负责持久化这些对象，但数据库里的所有内容不会每轮全部塞给模型。

成本为什么会增长

会议 01 指出，每次调用若都追加完整历史，Context 会不断累积，模型处理量与成本随之增大，最终触及上下文窗口限制。后续的裁剪、摘要和压缩，不是“可有可无的智能增强”，而是长会话迟早要面对的工程问题；但它不是第一垂直切片的前置条件。

常见误区

把“历史已写入 SQLite”当成“模型已经记住”。只有被 Context Builder 选中并放进本轮请求的信息，模型这一轮才能看见。

开发检查点

调试模型行为时，先保存并查看本轮 Context 的构成；不要只盯最终答案，也不要把数据库记录与模型可见内容混为一谈。

自检：能否画出本轮模型请求？

  2. Tool List 为什么属于 Context，而工具实现本身不属于？
  3. Session 中有 100 条历史，是否代表模型本轮看见 100 条？

04 · 约 9 分钟

Tool：模型能请求、Runtime 能执行的原子动作

本章问题：模型怎样知道工具存在，又怎样“调用”它？

一句话结论

工具由可执行实现和可给模型阅读的定义组成；模型只生成 ToolCall，Runtime 才负责校验、授权与执行。

一个工具至少要说清五件事

Tool
├── name             # 稳定名称，例如 read_file
├── description      # 什么时候使用、能做什么
├── inputSchema      # 参数结构与约束
├── permissionLevel  # 权限等级
└── execute(...)     # 真正执行的代码

会议用“天气搜索、网络搜索、读取文件、列出目录、创建/写入文件”解释工具：在计算机世界里，这些动作都可以封装成函数或脚本。模型看到的是名称、描述和参数要求；它根据任务生成调用参数。它不会直接跳进函数里操作电脑。

read_file 最小例子

给模型看的定义（示意，不绑定具体语言）：

{
  "name": "read_file",
  "description": "需要读取允许工作区内的文本文件时使用",
  "inputSchema": {
    "path": "string",
    "startLine": "integer | optional",
    "maxLines": "integer | optional"
  }
}

模型若判断需要文件内容，输出的是类似“调用 read_file，参数为某个 path”的结构化请求。Runtime 必须验证路径是否在 Workspace、参数是否合法、文件是否可读，再执行函数，返回内容或标准化错误。

模型负责

  • 判断是否需要工具
  • 选择工具
  • 生成参数
  • 读取结果后决定下一步

Runtime 负责

  • 校验 ToolCall
  • 检查权限
  • 执行与超时
  • 记录 Trace
  • 把结果写回 Context

描述与 Schema 为什么影响效果

会议 01 指出，模型要调得准，必须知道三件事：有哪些工具、何时使用、具体怎样传参。描述含糊会导致选错工具；参数 Schema 不清会导致调用失败。模型自身是否具备可靠 Tool Calling 能力也会影响参数生成，但 Runtime 仍不能因此省略校验。

常见误区

“模型返回了工具参数”不等于“工具执行成功”。ToolCall 是请求；真实结果可能是成功内容，也可能是路径越界、文件不存在、参数错误、超时或被用户拒绝。

开发检查点

第一个工具只做读取允许目录中的文本文件；先把成功、文件不存在、路径越界、内容过长四种结果结构定义清楚，不要一开始就接 Shell、网络与删除。

05 · 约 12 分钟

Agent Loop：判断、行动、观察，再判断

本章问题：一次 ToolCall 为什么还不算 Agent？

一句话结论

真正的闭环是：模型决定直接回答或请求工具；Runtime 执行；工具结果回填到消息历史；模型基于新证据再次决定，直到满足停止条件。

Model：判断
Final Response保存并结束
ToolCall校验 → 权限 → 执行
工具结果 / 错误 ↓
Observation：写回 Message List
↖ 再次组装 Context 并调用模型

用“写一份文档”走完整个例子

  1. 用户提出写文档的目标。
  2. 模型发现缺资料，先请求列出目录或读取文件。
  3. Runtime 执行工具，把目录或文件内容作为 Tool Result 追加回来。
  4. 模型发现读错文件，可以继续请求另一个文件。
  5. 证据足够后，模型请求写文件，Runtime 执行并回填结果。
  6. 模型看到目标和全部结果，判断是否可以给最终回答。

第一版可采用的伪代码

function runAgent(task, session, cancellationSignal):
  run = createAgentRun(task, session)

  for round from 1 to maxRounds:
    if cancellationSignal.cancelled:
      return finish(run, "cancelled")

    context = buildContext(session, run, availableTools)
    modelResult = provider.chat(context, timeout=modelTimeout)

    if modelResult.isFinalResponse:
      if completionPolicy.requiresValidation(run):
        appendValidationRequest(session, run)
        continue
      return finish(run, "completed", modelResult.text)

    if modelResult.isToolCall:
      checkedCall = validateSchemaAndPermission(modelResult.toolCall)
      toolResult = toolRuntime.execute(checkedCall, cancellationSignal)
      appendToolCallAndResult(session, run, checkedCall, toolResult)
      continue

    if modelResult.isError:
      if retryPolicy.canRetry(modelResult):
        continue
      return finish(run, "failed", modelResult.error)

  return finish(run, "max_rounds_reached")

伪代码明确写出四个防失控点：最大轮数、模型/工具超时、用户取消、以及完成前验证。设计文档还要求处理 Approval Required、重试、降级、暂停与恢复；第一垂直切片可以先保留清晰接口与状态，不必一次实现所有策略。

停止不是一句“我做好了”

会议 01 的关键追问是：模型声称任务完成，但可能没有按照项目文档检验，甚至“骗我”，怎么办？工程师的回答分两层：第一，模型能力会影响判断；第二，更可控的是 Context 和 Runtime。编码场景可以在模型准备结束时强制插入检查：重新读文件、运行代码、渲染页面或截图，再把验证结果送回主 Loop，让模型基于证据复判。

常见误区

把模型第一次返回的“已经完成”直接映射成 run.completed。若任务存在可执行验收，结束条件应依赖证据，而不是只依赖自然语言自报。

开发检查点

最小 Loop 的日志至少能还原：每轮输入构成、模型选择、ToolCall 参数、执行结果、错误、轮数、停止原因。否则出错时只能猜。

  2. Final Response 与 ToolCall 是哪一层作出的分叉？
  3. 最大轮数、取消和完成验证分别防什么风险？
  4. Tool 执行报错后，为什么错误本身也应作为 Observation 回填？

06 · 约 10 分钟

Runtime / Harness：让一次 AgentRun 真正跑起来

本章问题：Loop 之外，哪些工程机制是一运行就离不开的？

一句话结论

扩展为什么不能侵入 Core

设计原则要求：不同来源的工具最终都转换为统一 Tool 定义；来自 CLI、Cron 或未来 Webhook 的任务最终都转换为统一 AgentRun。MCP 是 Tool Runtime 的外部适配器，Cron 是 Trigger，Skill 注入方法与依赖。这样新增入口或扩展时，不必复制一套 Loop。

可观测性不是最后补日志

常见误区

每接一个新能力就写一条独立流程。例如让 Cron 直接调模型、MCP 自己维护另一套工具执行、UI 自己编排 Loop。这样很快会出现状态、权限和日志不一致。

为什么选择 read_file

  • 动作真实：模型训练数据里没有你本地这个文件，必须通过工具取得。
  • 链路完整：能够覆盖工具选择、参数、执行、Observation 回填和停止判断。
  • 风险较低：只读比写入、Shell、网络和删除更适合作为第一个能力。
  • 容易验收：可以准备一个固定文件和只有该文件包含的问题，判断回答是否有据可查。
  • 映射主场景：本地工作空间助手的后续目录分析、报告生成都从文件读取开始。

建议按这个顺序动手

  1. API 连通性：接一个模型 API，发固定 Input，保存原始 Output 与错误。
  2. 工具契约：定义 read_file 的 name、description、inputSchema、结果和错误。
  3. 工作区边界：仅允许读取明确 Workspace 内的文本文件，拒绝越界路径。
  4. 模型看见工具：把工具定义放入 Context，请求一个必须读取文件才能回答的任务。
  5. 执行与回填：解析 ToolCall，校验并执行，把结果作为工具消息追加。
  6. 再次调用模型：携带原任务、ToolCall 与 Tool Result，让模型生成最终答案。
  7. 停止保护：加入最大轮数、模型和工具超时、取消入口及明确停止原因。
  8. 验收记录：保存每轮 Context 摘要、ToolCall、Result、最终回答、耗时和错误。

第一垂直切片的验收单

  • 不给模型文件正文，只给任务和工具定义。
  • 模型确实返回 read_file ToolCall，而不是假装读过。
  • 路径合法时读取成功；不存在或越界时返回结构化错误。

  • 工具失败后模型能看到错误并合理结束或调整，而不是死循环。
  • 达到最大轮数、超时或取消时，AgentRun 有明确状态。
  • 运行记录足够让你复盘“为什么调工具、拿到什么、为什么结束”。

设计文档把 Session 定义为“一段连续交互及其元数据”。会议 01 在结束前补充：个人助手需要管理自己的多个会话，每个会话的上下文隔离，本质上需要一套数据库管理。Phase 2 再用 SQLite 持久化 Session、Message、ToolCall 和 AgentRun，让程序重启后仍能查看与继续。

Memory 的四层建议

  • Short-term Memory：当前上下文窗口里的近期消息。
  • Session Memory：当前会话摘要与任务状态。
  • Long-term Memory：跨会话的用户偏好和稳定事实。
  • Workspace Memory：某个本地项目的约定、背景与经验。

会议 02 将短期记忆解释为不断追加的 Message List，把跨会话或跨周期信息归为长期记忆。设计文档更细地拆为四层。二者并不冲突：会议是入门二分法，设计文档是项目落地分层。

存储策略的阶段边界

第一版建议 SQLite 保存结构化数据，Artifact 单独放在 Workspace 目录；向量检索不是首期必需。第一个单工具 Loop 可以先使用内存中的消息列表，直到 Phase 2 才要求程序重启后恢复。接口命名要为 Session 与 AgentRun 留出边界，但不能因为未来要持久化，就提前把第一切片做成完整数据库项目。

常见误区

把所有历史都叫 Memory，或把 Memory 当成一个永远自动正确的文件。记忆价值取决于抽取、保留、检索和重新注入策略；原文会话记录通常仍需单独保留。

方法论必须回到工程实践

用户追问压缩策略来自模型交互还是人类经验。工程师回答“两者都有”，但最终要回到工程实践和评测基准：行业经验可以提出候选策略，模型可以执行摘要，真正决定好坏的是任务能否继续、关键事实是否保留、错误是否减少。若评测基准歪了，就可能“实际更差，但自以为更好”。

压缩风险

摘要一旦把“尚未完成”写成“已完成”，或者删除了用户约束，后续模型会在错误状态上继续。压缩输出需要结构校验、关键字段检查，并保留可回溯的原始会话。

  2. 已完成、进行中、未开始三类任务是否被正确区分？
  3. 用户限制、失败原因和 Artifact 路径是否仍在？
  4. 压缩节省了多少 Token，是否以任务成功率为代价？

会议中的 memory.md 做法

Tool Runtime 与权限：工具越多，越不能各自为政

如果有 100 个工具，谁负责让它们以同一套规则运行？

一句话结论

Tool Runtime 把不同来源的工具统一注册、发现、校验、授权、执行、取消、截断、报错和记录；安全边界必须走这条主链。

从“一个函数”升级为“可控执行系统”

  • 注册、发现、命名去重与能力声明。
  • 依据 JSON Schema 校验模型参数。
  • 权限策略与用户确认。
  • 执行、取消、超时和并发边界。
  • 结果长度控制、截断与 Artifact 化。
  • 成功/错误统一结构。
  • ToolCall 日志、事件与 Trace。

读、写、删不是同一种风险

设计文档建议的权限等级
风险示例默认策略会议中的直观解释
低查看目录、读取允许目录内文件可自动执行read_file 通常可较自由使用
中写文件、安装依赖、访问网络按策略确认write 多数时候先请求审批
高删除、危险 Shell、发送外部消息必须确认delete 应逐次向用户确认

会议还用 Read Only、Workspace Write、Full Access 三档解释工具权限，与某些产品的“极简/标准/其他 Harness 模式”不是一回事：前者决定工具能执行到哪里，后者可能改变 System Prompt 和 Tool List 的整体配置。

极简与标准 Harness 的会议例子

工程师举例：极简模式可能只有 Bash 和编辑类两个工具，System Prompt 也很短，因此速度快、适合在简洁内核上二次扩展；标准模式会有更完整的工具集，例如网络搜索。该段是在解释“框架配置模式”，不是本项目已确认要复制的产品规格。

Security 还包括什么

  • Workspace 访问边界和真实目标展示。
  • 命令参数展示与危险操作审批。
  • Secret 与模型 Context 隔离。
  • Built-in、User Tool、MCP Tool 的来源与信任状态。
  • 敏感输出脱敏、运行取消和超时保护。

常见误区

把权限提示只做在 UI 上。UI 可以显示确认，但真正的拒绝必须发生在 Tool Runtime 执行前；否则换一个入口或后台 Trigger 就可能绕过。

Phase 3 完成标准

危险操作必须确认；工具失败后，Agent 能读到标准化错误并调整下一步行为；Workspace 边界、超时、取消、结果截断与统一记录均可验证。

完成条件、验证与评测基准：防止“模型说做完了”

怎样把“我觉得完成”变成可核验的完成？

一句话结论

任务完成要尽量绑定外部证据；优化策略要绑定能代表真实质量的评测基准。

完成判断受两类因素影响

  1. 模型本身能力：不同模型在推理、Tool Calling 和代码任务上的可靠性不同。
  2. 模型实际看见的 Context：目标、规则、结果、错误和验收标准是否被清楚放入。

模型能力不是 Runtime 能直接改变的，但可以通过 Provider 的能力声明选择合适模型；Context、停止策略和验证注入则是项目可控的工程空间。

会议中的“结束前强制检查”

工程师以编码任务举例：主模型准备结束时，Runtime 可以强制插入验证请求，让它重新读取写出的文件、运行代码，前端任务还可以渲染页面并截图检查。验证产物回填同一主 Loop，模型重新判断是否真的完成。也可以先用小模型做任务分类，只在 Coding 场景启用对应验证策略；这是高级优化示例，不是首切片必需。

风险优先级

  1. Loop 是否正确结束，是否会无限循环。

Provider 与模型能力：API 能连通，不等于抽象完成

怎样让 Agent Core 不被某一家模型服务绑死？

一句话结论

Provider 把不同模型服务的消息、Tool Calling、流式事件、错误、Usage 与能力声明转换成 Agent Core 的统一协议。

ModelProvider
├── chat(request)
├── stream(request)
├── listModels()
└── getCapabilities(model)

统一接口至少处理什么

  • 消息角色与格式转换。
  • Tool Calling Schema 与结果格式转换。
  • 流式输出事件。
  • Usage、Token 与成本信息标准化。
  • 错误、限流、超时与重试标准化。
  • 模型能力声明，以及 API Key、Base URL 和参数管理。

为什么先一个，再第二个

设计文档建议先支持一个云端 Provider，跑通闭环后再加入一个 OpenAI-compatible 或本地模型 Provider。Phase 4 的完成标准是“不修改 Agent Core 即可切换 Provider”。如果第一天就适配多家，往往只得到一堆条件分支，却还没证明核心协议真的正确。

依赖能力，不依赖模型名字

会议 01 解释了 Tool Calling 是模型生成结构化工具参数的能力；不同模型会影响完成判断与调用质量。设计文档因此要求 Agent 查询 Capability，而不是用模型名称硬编码判断“这个能不能 Tool Calling”。

应用层产品与构建层产品

用户在会议 01 追问“自己接 API”和“在现成 Agent 产品里选模型”有什么区别。工程师区分了开箱即用的应用层产品与允许开发者接模型、做二次开发的构建层产品。本项目属于后者：必须自己理解模型 API 请求与响应，而不是只在某个已有界面中选择模型。

时效说明

会议 02 讨论了某具体模型 API 的价格与推荐。这是会议发生时的工程师观点，价格和产品状态会变化；本手册不把它改写成当前采购结论，也不替项目选择供应商。

Phase 4 验收

同一个 Agent Core、同一个 Tool 定义和同一场景测试，在切换 Provider 后仍能完成；差异只留在适配层，错误与 Usage 采用统一结构。

MCP、Skill、RAG/知识库和 Cron：都要回到统一主链

这些热门概念分别接在哪，为什么不属于第一最小闭环？

一句话结论

MCP 最终适配成内部 Tool/Resource，Skill 向 Context 和工具注册表注入方法与依赖，RAG 通过 Context 或检索 Tool 提供证据，Cron 作为 Trigger 创建 AgentRun。

四类扩展的边界
概念本质进入主链的位置没有它能否跑首个 Loop
MCP外部 Server 能力的协议与连接方式MCP Client → Schema 转换 → Tool Registry能
Skill某类任务的方法、步骤、约束和依赖包指令进入 Context，依赖工具进入 Registry能
RAG / 知识库外部知识的存储、加工与检索检索结果直接进 Context，或通过检索 Tool 回填能
Cron按时间创建任务的 TriggerScheduler → AgentRun → 标准 Loop能

MCP：外部适配器，不侵入 Agent Core

设计文档要求支持 Server 配置与启停、stdio/HTTP 等连接、Tools/Resources/Prompts 发现、Schema 转换、断线/超时/进程退出、信任等级、权限与日志。其关键不是“能连一个 Server”，而是外部能力转换成内部统一对象后，继续走相同 Tool Runtime。

Skill：方法包，不是原子动作

Skill 可以包含 SKILL.md、manifest、可选工具、提示词、脚本和参考资料。它负责告诉 Agent 一类任务该按什么步骤与约束完成，并声明所需能力。边界口诀是：Tool 是原子动作，Skill 是完成一类任务的方法，Agent 是执行目标与策略的主体。

RAG：最后仍是模型可见证据

会议 01 用非常直接的方式解释：模型输出只有最终回答或工具参数；若知识检索不是事先注入 Context，就只能由模型请求检索工具，结果再回填。会议中的“reg”大概率指 RAG，但保留在转写纠错表，不把每个模糊词静默改写。

Cron：改变触发时间，不改变执行内核

会议 02 的“每天 8 点看金价”例子包含任务内容、时间、运行位置、所属会话和频率。时间到后，调度器把任务注入标准 Loop，可能带上定时任务标签或相应 System Prompt。设计文档进一步要求一次性/周期任务、启停、并发、超时、重试、历史与通知。未来 Webhook 也复用 Trigger → AgentRun。

范围判断

这些能力都很适合作为后续里程碑展示，但它们不能替代单 Provider、ToolCall、执行、回填和停止条件。先做扩展，会把尚未稳定的主链复制到更多入口。

扩展接入前检查
  • 能否转换成统一 Tool、Context 信息或 AgentRun？
  • 是否复用同一权限、错误、取消和事件机制？
  • 卸载扩展后，Agent Core 是否仍能正常运行？

产品形态与企业交付：先问业务如何工作

同一套内核为什么可以长成对话框、表单或工作流？

一句话结论

内核提供可靠智能与行动能力；行业、业务场景、可信数据、现有生态和工作流程决定最终产品形态。

会议中的企业交付三层逻辑

  1. 需求层：企业是什么行业、什么业务场景、当前生态怎样、底层框架需要解决什么。
  2. 能力层：Agent 能否基于可信外部数据完成有效分析与行动。
  3. 产品层：能力应嵌入对话入口、网页点选、传统表单、工作流节点，还是其他业务流程。

用户用之前的文旅 AI 项目追问企业交付。工程师指出，最核心的是 Agent 的智能能力是否能利用可信数据做有效分析；至于长成智能助手页面、点选式网页还是工作流产品，是应用形态问题。会议还用 GTM 场景举例：AI 可以融入市场营销和销售流程，主要交互未必是对话。

为什么过程轨迹是产品能力

项目不仅要显示最终答案，还要展示会话管理、Context 持久化、工具调用与事件流。对用户，这提供进度、确认和错误解释；对开发者，它揭示执行链路；对企业，它支持审计、信任和故障复盘。设计文档因此把“一切执行均可追踪”列为核心原则。

交互层的责任边界

  • 创建、选择、恢复 Session。
  • 接收自然语言任务，展示流式输出。
  • 展示 ToolCall、运行进度、异常与 Artifact。
  • 处理确认、取消与中断。
  • 不直接编排 Agent Loop。

Agent 核心术语表

本项目统一用语与边界
规范术语教学定义边界提醒
Model接收输入并生成输出的模型本体。不负责真实工具执行和长期状态保存。
Provider把不同模型 API 转换为统一请求、响应、流式事件、错误和能力声明的适配层。Agent Core 不应硬编码供应商协议。
Agent一组模型、提示词、工具和策略配置所描述的执行主体。不是某一次任务运行。
AgentRun一次从任务开始到完成、失败、取消或暂停的具体运行。同一 Session 可有多个 Run。
Agent Loop模型判断、行动、观察结果并再次判断的循环。必须有停止、超时与取消。
Runtime让一次 AgentRun 能真实运行所需的核心工程机制。不同团队定义可能有宽窄差异。
Harness会议中用于描述模型外部工程框架或脚手架的词。本项目正式名称统一为 Local Agent Runtime。
Context一轮模型调用可见的提示词、消息、工具、记忆和运行状态集合。不等于数据库全部内容。
Session连续交互及其消息、运行、工具调用、产物和摘要的容器。不同 Session 的 Context 应隔离。
Memory被保存、压缩、检索并重新放入 Context 的信息。文件或向量库只是载体。
ToolAgent 可以请求执行的一项原子操作。不同于一整套任务方法。
ToolCall模型对某个工具及其参数的一次调用请求与结果记录。请求不等于已经执行成功。
Tool Runtime负责工具注册、校验、权限、执行、取消、错误和日志的系统。所有工具来源最终走统一主链。
Skill完成某类任务的方法、约束和能力依赖包。不等同于原子 Tool。
MCP将外部 Server 的 Tool、Resource 或 Prompt 适配进内部系统的协议与连接方式。不应直接侵入 Agent Core。
Trigger创建 AgentRun 的触发来源，如 CLI、Cron 或未来 Webhook。不拥有独立 Loop。
ArtifactAgent 生成的文件、报告或其他持久化产物。与最终聊天文本可并存。
Event / Trace描述运行状态变化和完整执行链路的结构化记录。用于 UI、调试、审计和评测。
