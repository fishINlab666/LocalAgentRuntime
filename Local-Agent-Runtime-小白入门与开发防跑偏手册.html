01 · 约 8 分钟

这个项目究竟要做什么

本章问题：为什么“会聊天”远远不等于做出了这个项目？

一句话结论

Local Agent Runtime 是模型外部的一套运行系统：它让模型能在个人电脑上持续接收任务、选择工具、执行真实动作、保存过程、处理权限与错误，直到形成可检查的回答或 Artifact。

项目的正式定位

设计文档把它定位为“个人本地智能助手框架”，主要运行在个人电脑。用户可以通过 CLI 或桌面界面交流；Agent 可以调用本地或外部工具，管理连续会话，并通过 MCP、Skill、Cron 扩展能力。它同时是一件求职作品：不仅能演示，还要让面试官看见工程闭环、边界、安全与演进路径。

贯穿项目的演示场景

  1. 用户要求 Agent 分析一个本地项目。
  2. Agent 查看目录和文件，必要时执行命令。
  3. 经历多轮 Tool Call 后，生成报告或修改建议。
  4. 会话、模型调用、工具轨迹与产物被保存。
  5. 程序重启后，用户能恢复并继续任务。
  6. 后续用 Skill 增加工作流，用 MCP 接第三方工具，用 Cron 定期检查。

内核和外壳不是一回事

会议 01 反复强调：对话框、CLI、工作流节点、传统表单都只是上层产品形态；真正决定智能效果的是底层内核能否基于可信数据完成有效分析。企业交付时，要先理解行业、业务场景、现有生态和工作流程，再决定把能力包装成什么样。不能因为市面上常见对话入口，就误以为 Agent 产品必然长成聊天窗口。

设计文档的首版建议

Interaction Layer 第一版建议只做 CLI，核心稳定后再增加桌面界面。

会议中明确出现的用户偏好

用户不偏好 CLI；会议也接受内核完成后包一层简单页面。

教学解释：怎样不让差异阻塞开工

第一垂直切片先用最薄的脚本、测试或调试入口验证内核；是否补 CLI 或简单页面，是后续演示选择，不应抢在 Loop 前面。

完整项目的目标能力（分阶段建设）

以下是设计方案的完整目标，不是第一切片必须一次实现的清单，也不是这些功能已经全部完成的声明。

  • 完整 Agent Loop，而非单轮聊天封装。
  • 统一 Tool Runtime，让模型安全操作外部环境。
  • Provider 层屏蔽云端或本地模型差异。
  • Session、Context、运行状态和长期记忆管理。
  • MCP、Skill、Cron 的统一扩展与触发机制。
  • 模型调用、工具执行、异常、Token 和成本可观测。
  • 本地文件、Shell、网络和删除操作具有权限边界。

常见误区

先做一个漂亮聊天页面，再把 API 接进去。这只能证明“界面能请求模型”，不能证明工具闭环、状态、安全、恢复和可观测性成立。

开发检查点

任何新需求先问：它属于 Runtime 核心、扩展层，还是交互外壳？如果只是外壳，是否会阻塞当前最小闭环？

02 · 约 8 分钟

从大模型到 Agent：多出来的到底是什么

本章问题：为什么一个能生成文本的模型，还需要 Runtime 才能成为可工作的 Agent？

一句话结论

模型本体接收输入、生成输出；Agent 系统在它外面补上实时信息、状态连续性和真实行动能力。

先把模型看成一个“输入 → 输出”的函数

会议 01 从生成式 AI 的本质讲起：模型基于训练阶段学到的模式，对输入生成文本或其他多模态输出。对工程入门来说，先把它理解为一次 API 调用最有用——本次请求给它什么，它本次就看见什么；它不会因为你上一次调用过，就天然记住上一次内容。

会议归纳的三个局限

01 数据不实时

训练数据有时间边界。需要 Web Search 或业务数据工具，把新信息取回来。

02 没有天然状态与记忆

在本项目自行组装请求的方式下，历史需要由应用重新带入。服务端也可以代管会话，但最终仍需把有关材料送入本轮推理；不是模型本体永久记忆。

03 不能亲自做事

模型只能生成输出；真正读文件、运行命令或写报告的是 Runtime 中的工具执行代码。

Agent 不是一个更神秘的模型

在本项目中，Agent 描述的是模型、提示词、工具和策略的组合；一次具体任务叫 AgentRun。模型仍然只输出文本或 ToolCall 参数。Runtime 解析输出、执行工具、把结果写回，再询问模型下一步。所谓“自主”，来自这个受控循环，不是模型突然拥有了电脑权限。

教学解释

类比：模型像只负责判断与写指令的“大脑”，Tool 是可调用的动作，Context 是桌面上摊开的全部材料，Runtime 是按规则递送材料、执行动作、记录过程并踩刹车的运行系统。类比只帮助分工，不意味着模型真的拥有人的意识。

常见误区

把“模型能力强”直接等同于“Agent 工程可靠”。模型会影响判断质量，但工具参数校验、权限、重试、状态、停止条件和 Trace 都是外部工程责任。

开发检查点

看到任何“Agent 能做 X”的需求，都拆成三问：模型需要看见什么？它要请求哪个原子动作？Runtime 怎样安全执行并把证据送回去？

自检：模型本体没有哪三样东西？
  1. 为什么第二次 API 调用不会天然知道第一次聊了什么？
  2. Web Search 解决的是哪一类局限？
  3. 本地文件真正由谁读取：模型还是工具代码？
参考答案与判断依据 · 模型本体的边界
  1. 独立模型调用只处理本轮输入。应用或服务端会话机制要把历史带入下一轮，才有连续性；不因“同一个 Agent”就自动共享全部历史。
  2. Web Search 获取可访问的外部网页信息，包括新发布和既有资料，补充训练知识的时效与覆盖局限。它不自动解决长期记忆，也不能读取所有私有数据。
  3. 读取由工具代码完成。模型生成请求，Runtime 校验和执行，结果回填后模型才获得文件内容。

03 · 约 9 分钟

Context：模型这一轮实际看见的全部材料

本章问题：无状态 API 为什么能表现得像“记得前文”？

承接第 02 章：模型本轮能用的信息来自本轮输入。现在只解决一件事——程序怎样把前文和工具结果放进这份输入；暂时不需要实现长期记忆或摘要。

一句话结论

不是模型在后台偷偷记住你，而是应用在每轮调用前重新组装 Context。

从单个 Input 扩展成 Context

会议 01 先用两轮对话解释：第一轮问某人的新闻，第二轮只问“他今年多大”，如果第二次只发送这一句，模型不知道“他”是谁；若把第一轮 User、Assistant 和第二轮 User 依序放进 Message List，模型就能从本次请求里解析指代。

教学解释

先用原文追加就能产生短期连续性。第一轮发送“请读取项目设计文档”；第二轮把原问题、模型的读取请求和工具返回的内容一起发送。模型从本次输入得知刚才发生了什么。压缩用于历史太长时节省空间，不是连续性的起点。

第 1 次模型请求：规则 + 用户问题 + 可用工具定义
第 2 次模型请求：规则 + 用户问题 + 工具调用请求 + 工具返回结果 + 可用工具定义

Tool List 是本轮可选动作的说明；已经用过的工具及其结果属于消息历史。工具定义可能通过 API 的单独字段发送，仍属于本轮模型可见材料。

下面是目标架构可能组装的材料。Skill、摘要、长期 Memory 只在具备对应能力且本轮需要时加入，不是每轮的必填项。

Context 不是数据库，也不是 Session

Context 是某一轮请求实际送给模型的集合；Session 是保存连续交互、运行、工具调用、Artifact 和摘要的容器；Memory 是被保存、加工、检索，并在需要时重新放进 Context 的信息。数据库负责持久化这些对象，但数据库里的所有内容不会每轮全部塞给模型。

Session 有 100 条历史，这次到底选哪些？

可能全部选中，也可能只选一部分；“存有 100 条”本身无法回答。决定因素包括模型输入预算、当前目标、近期往返、相关资料，以及必须保留的用户约束和工具调用关系。具体策略由 Context Builder 的程序逻辑制定，原材料没有确认唯一算法。

教学解释 · 最小选择策略示意
  1. 先保留本次目标、关键限制和本轮可用工具。
  2. 保留最近的交互，尤其是还要用到的工具请求与结果，并按原调用 ID 配对。
  3. 有余量再加入相关旧消息或检索结果；空间不足时才裁剪较旧内容或生成摘要。
  4. 相关事实放不下时应明确缺失、再按需读取，不能用摘要替代未经验证的原文事实。

Session 在交互过程中持续保存；Context Builder 在每次模型请求前组装；压缩通常在预算不足时介入；长期记忆在需要跨会话信息时保存或检索。短历史的第一个 Loop 可以完全不触发后两项。

成本为什么会增长

会议 01 指出，每次调用若都追加完整历史，Context 会不断累积，模型处理量与成本随之增大，最终触及上下文窗口限制。后续的裁剪、摘要和压缩，不是“可有可无的智能增强”，而是长会话迟早要面对的工程问题；但它不是第一垂直切片的前置条件。

常见误区

把“历史已写入 SQLite”当成“模型已经记住”。只有被 Context Builder 选中并放进本轮请求的信息，模型这一轮才能看见。

开发检查点

调试模型行为时，先保存并查看本轮 Context 的构成；不要只盯最终答案，也不要把数据库记录与模型可见内容混为一谈。

自检：能否画出本轮模型请求？
  1. Message List 如何制造短期连续性？
  2. Tool List 为什么属于 Context，而工具实现本身不属于？
  3. Session 中有 100 条历史，是否代表模型本轮看见 100 条？
参考答案与判断依据 · 不必先压缩才有连续性
  1. 把上一轮相关消息再次发送，模型就能在本轮输入里读到前文。短历史可直接追加；摘要和压缩用于历史变长后的预算管理。
  2. Tool List 描述本轮可选工具及其调用方式，因此必须让模型看见；实际执行代码留在运行系统中。Tool List 不是使用记录。
  3. 不代表。模型看到的是本轮实际选中的材料；100 条可能全部放得下，也可能需要筛选。选择依据包括目标、预算、近期往返和调用/结果配对，原设计未规定唯一算法。

04 · 约 9 分钟

Tool：模型能请求、Runtime 能执行的原子动作

本章问题：模型怎样知道工具存在，又怎样“调用”它？

一句话结论

工具由可执行实现和可给模型阅读的定义组成；模型只生成 ToolCall，Runtime 才负责校验、授权与执行。

一个工具至少要说清五件事

Tool
├── name             # 稳定名称，例如 read_file
├── description      # 什么时候使用、能做什么
├── inputSchema      # 参数结构与约束
├── permissionLevel  # 权限等级
└── execute(...)     # 真正执行的代码

会议用“天气搜索、网络搜索、读取文件、列出目录、创建/写入文件”解释工具：在计算机世界里，这些动作都可以封装成函数或脚本。模型看到的是名称、描述和参数要求；它根据任务生成调用参数。它不会直接跳进函数里操作电脑。

read_file 最小例子

给模型看的定义（示意，不绑定具体语言）：

{
  "name": "read_file",
  "description": "需要读取允许工作区内的文本文件时使用",
  "inputSchema": {
    "path": "string",
    "startLine": "integer | optional",
    "maxLines": "integer | optional"
  }
}

描述与 Schema 为什么影响效果

会议 01 指出，模型要调得准，必须知道三件事：有哪些工具、何时使用、具体怎样传参。描述含糊会导致选错工具；参数 Schema 不清会导致调用失败。模型自身是否具备可靠 Tool Calling 能力也会影响参数生成，但 Runtime 仍不能因此省略校验。

教学解释

描述帮助选工具；Schema 帮助填参数。“需要本地文本内容时调用 read_file”告诉模型什么时候用；“path 必填且是字符串”告诉模型怎么填写。只有描述，可能选对工具却填错参数；只有参数格式，可能不知道何时该选它。上方 inputSchema 是便于阅读的简写，不是可直接复制使用的完整 JSON Schema。

参数正确也不等于获得授权。文件存在，仍可能位于禁止访问的目录；函数能够执行，仍可能有删除或发送消息的副作用。Tool Runtime 要执行参数、权限和运行边界检查。需要批准的操作，应在执行前取得批准。

常见误区

“模型返回了工具参数”不等于“工具执行成功”。ToolCall 是请求；真实结果可能是成功内容，也可能是路径越界、文件不存在、参数错误、超时或被用户拒绝。

开发检查点

用“写一份文档”走完整个例子

  1. 用户提出写文档的目标。
  2. 模型发现缺资料，先请求列出目录或读取文件。
  3. Runtime 执行工具，把目录或文件内容作为 Tool Result 追加回来。
  4. 模型发现读错文件，可以继续请求另一个文件。
  5. 证据足够后，模型请求写文件，Runtime 执行并回填结果。
  6. 模型看到目标和全部结果，判断是否可以给最终回答。

回填的作用：把行动变成模型可见的证据

模型只看见 ToolCall 时，最多知道“曾请求读取”，不能据此确认执行成功，更不知道文件内容。如果连请求记录也没有进入本轮 Context，它也不知道自己请求过。Runtime 要把成功或错误按原调用 ID 关联，并交给 Context Builder 带入下一轮。

例如，读取返回“文件不存在”，模型才有依据修正路径、请求列目录或说明无法完成。给模型的错误应保留可恢复信息并脱敏；给开发者的诊断日志可以记录更完整的内部细节。回填首先服务于下一步判断，也服务于复盘。

分叉有两个责任：模型基于 Context 生成最终回答或工具请求；Agent Core 解析结果并执行相应分支。Context 是判断材料，Loop 是控制流程，二者不应混叫。

教学解释：下面表示职责与分支，不是仓库里可直接调用的函数或已确认 API。单轮可能含多个工具请求；本例顺序执行。重试也须受次数、时间和取消约束。

function runAgent(task, session, cancellationSignal):
  run = createAgentRun(task, session)

  for round from 1 to maxRounds:
    if cancellationSignal.cancelled:
      return finish(run, "cancelled")

    context = buildContext(session, run, availableTools)
    modelResult = callModelWithBoundedRetry(context, modelTimeout, cancellationSignal)

    if cancellationSignal.cancelled:
      return finish(run, "cancelled")
    if modelResult.isError:
      return finish(run, "failed", modelResult.error)

    if modelResult.hasToolCalls:
      appendAssistantToolCalls(session, modelResult.toolCalls)
      for call in modelResult.toolCalls:
        # 校验失败、权限拒绝、超时和执行失败都产生标准化结果
        # 若已取消，剩余请求标记为未执行，不继续启动工具
        result = executeCheckedToolOrError(call, cancellationSignal, toolTimeout)
        appendToolResult(session, toolCallId=call.id, result=result)
      if cancellationSignal.cancelled:
        return finish(run, "cancelled")
      continue

    if modelResult.isFinalResponse:
      verdict = completionPolicy.checkEvidence(run, modelResult)
      if verdict.passed:
        return finish(run, "completed", modelResult.text)
      if verdict.canContinue:
        appendConcreteValidationRequest(session, verdict.missingEvidence)
        continue
      return finish(run, "incomplete", verdict.reason)

    return finish(run, "failed", "unrecognized_model_result")

  return finish(run, "max_rounds_reached")

executeCheckedToolOrError 在这里代表校验、权限、必要的用户确认和受控执行；可恢复错误与成功内容都按调用 ID 返回。取消后仍保存已知结果与未执行状态，但不为“继续回填”而再调用模型。审批等待也要能取消或超时。

checkEvidence 依据本次实际结果更新判断：验证通过才结束，缺证据且可继续才请求具体检查；后续修改使旧证据失效时应重新检查。完成验证和错误恢复都占用总运行预算，不能反复注入同一句“请检查”却永远不记录检查结果。设计还要求 Approval Required、重试、降级、暂停与恢复；完整策略分阶段实现。

机制防的风险例子

停止不是一句“我做好了”

会议 01 的关键追问是：模型声称任务完成，但可能没有按照项目文档检验，甚至“骗我”，怎么办？工程师的回答分两层：第一，模型能力会影响判断；第二，更可控的是 Context 和 Runtime。编码场景可以在模型准备结束时强制插入检查：重新读文件、运行代码、渲染页面或截图，再把验证结果送回主 Loop，让模型基于证据复判。

你提出：“读取项目设计文档，告诉我 Phase 1 的完成标准。”这次只要求读取和回答，不要求生成新文件。

1. 哪项任务正在进行：AgentRun 与状态

同一段会话里，你可以先要求总结设计，再要求比较会议建议。程序需要分清各项执行的开始、完成、失败和取消。一次具体的任务执行叫 AgentRun；其中可以调用模型多轮、执行多个工具。一次模型请求并不等于一次完整任务。

配置好的助手叫 Agent，描述用哪个模型、哪些提示词、工具和策略；保存这段连续交互的容器叫 Session。同一个 Agent 可执行多次 AgentRun，同一个 Session 也可保存多次运行。

Agent：助手使用的模型、提示词、工具与策略配置
Session：围绕项目的连续交互
  ├─ AgentRun A：读取设计并回答（可能包含多轮模型调用）
  └─ AgentRun B：比较会议建议（有自己的运行记录）

“正在运行、等待审批、已完成、失败”等是运行状态（Run State）的教学例子。记录状态后，页面能显示进度，用户取消时也能定位具体任务。暂停后继续同一任务、失败后重试一次动作、重启后恢复会话是不同能力；原设计没有规定全部状态枚举和断点恢复细节。

2. 谁推动下一步：Agent Core 与策略

Agent Core 是任务总控程序。它推进 Loop：先组织模型请求，再解析返回类型；遇到工具请求就交给执行侧，收到结果就保存并准备下一轮。模型选择行动，总控执行流程分支。

“策略（Policy）”可以先理解为处理规则：Stop Policy 规定何时停，Retry Policy 规定哪些失败能再试，Approval Policy 规定何时先问用户。它们由程序执行，不能仅靠模型自觉遵守。四种保护的区别见第 05 章。

3. 程序手里的信息与模型看见的信息

处理任务时，程序需要知道属于哪个 Session、允许访问哪里、用了什么配置、当前状态是什么。RunContext 汇总本次执行所需的会话、配置、权限和状态。它是运行用的信息集合，不是一份必须原样发给模型的长提示词。

真正发给模型的材料叫 Context。Context Builder 根据本次目标和预算选择消息、规则、工具定义和必要资料。例如第二轮加入读取结果，模型才有原文可参考。

同一次读取中，两种 Context 的用途
信息集合谁使用例子
RunContext后台程序执行任务当前会话、权限、配置、运行状态

程序收到取消信号，要执行停止逻辑；不能只把“请取消”发给模型后等待它配合。权限同理：必要限制可告诉模型，但实际路径仍须由程序检查。保存过的信息是否进入下一轮，取决于组装过程，见第 03 章。

4. 总控分别连接模型和工具

不同模型 API 的消息、工具格式和返回可能不同。Provider 是模型服务适配层：把总控的统一请求转换成具体服务要求的格式，再把响应转回统一格式。因此更换模型服务时，不应要求重写整个 Loop。

Tool Runtime 管理工具执行。它按工具名查找实现，校验参数、权限和路径，必要时等待批准，再执行并返回标准化结果；也负责超时、取消、结果长度和调用记录。read_file 函数承担实际文件读取。

Agent Core（任务总控）
  ├─ Provider → 模型服务 → 返回判断 / 工具请求
  └─ Tool Runtime → read_file 等工具代码 → 返回实际结果 / 错误

本例中，工具内容保存到 Session，再进入下一轮模型 Context。模型给出最终回答后，总控按完成策略判断是否可以结束；缺少必要证据时继续或合理终止，不把一句“完成了”直接当作成功。

5. 怎么知道过程：Event、Trace 与 Artifact

后台开始读取后，界面需要知道“正在读”，出现错误时也需要显示原因。程序因此发布事件（Event），记录某一刻发生的事情；关联同一次运行的事件、模型与工具记录，就能形成执行轨迹（Trace）。任务生成并保存的报告或文件，则叫Artifact，交付物。

三者在同一个实例里的区别
对象内容用途
Eventtool.completed：一次工具执行结束记录变化、更新界面；是否成功仍需看结果状态
Trace请求了什么文件、实际返回什么、为何结束复盘整次任务、定位错误和耗时

本次只读取并回答，可以没有新 Artifact。可观测性（Observability）就是让人能看见运行证据；事件分发机制（Event Bus）把记录送到界面或日志等接收方。结构化事件有固定字段含义，便于程序关联任务；不是必须先搭一个复杂消息系统。

MCP 是连接外部工具的标准方式之一，在本项目通过适配器进入内部工具系统；Skill 补充任务方法、约束和工具依赖；知识库提供可检索资料；Hooks 在约定节点加入处理。它们增强已有主链，不各自复制一套 Loop，细节放在第 16 章。

UI 同时有输入和展示职责。它接收任务、批准、拒绝和取消，再消费事件显示进度；“不编排 Loop”是指不自行决定下一步调用哪个工具。否则页面、命令行和定时任务可能各有不同的权限和停止规则。

Agent模型、提示词、工具与策略的配置主体不是某一次具体运行
AgentRun可完成、失败、取消、暂停或恢复的一次任务不是整段会话本身

Artifact报告、文件或其他持久化产物不等于最终聊天回复

横向能力贯穿多处：Configuration 保存运行设置，Storage 保存数据，Security 约束访问与执行，Event Bus / Observability 提供过程信息。SQLite 是后续持久化的一种实现；第一个 Loop 可先在内存保存消息。职责存在，不代表首日就要建设所有模块、长期记忆或重启恢复。

常见误区

每接一个新能力就写一条独立流程。例如让 Cron 直接调模型、MCP 自己维护另一套工具执行、UI 自己编排 Loop。这样很快会出现状态、权限和日志不一致。

开发检查点

新增能力前，明确它落入哪条统一通道：模型差异走 Provider；动作走 Tool；外部工具走 MCP→Tool；定时任务走 Trigger→AgentRun；界面提交用户操作并消费 Event，不自行编排 Loop。

自检：Runtime 的边界在哪里？
  1. Cron 到点后为什么不应该拥有另一套 Agent Loop？
  2. UI 可以提交哪些操作？为什么不直接决定下一步调用哪个工具？
  3. Event 与 Artifact 的区别是什么？
参考答案与判断依据 · 用一次任务检验理解
  1. Cron 负责到点发起任务，再交给统一 AgentRun 和 Loop；共用权限、状态、停止条件与记录，避免另一套规则。
  2. UI 可以提交任务、批准、拒绝和取消，并展示事件。模型提出动作，Core 管理流程，工具执行由 Tool Runtime 约束；换界面不应复制调度逻辑。
  3. Event 记录过程中的一件事，Trace 关联整次运行，Artifact 是实际生成并保存的文件或报告。只读取并回答时可以没有新 Artifact。

为什么选择 read_file

  • 动作真实：模型训练数据里没有你本地这个文件，必须通过工具取得。

  • 风险较低：只读比写入、Shell、网络和删除更适合作为第一个能力。
  • 容易验收：可以准备一个固定文件和只有该文件包含的问题，判断回答是否有据可查。
  • 映射主场景：本地工作空间助手的后续目录分析、报告生成都从文件读取开始。

建议按这个顺序动手

  1. API 连通性：接一个模型 API，发固定 Input，保存原始 Output 与错误。

  4. 模型看见工具：把工具定义放入 Context，请求一个必须读取文件才能回答的任务。
  5. 执行与回填：解析 ToolCall，校验并执行，把结果作为工具消息追加。
  6. 再次调用模型：携带原任务、ToolCall 与 Tool Result，让模型生成最终答案。
  7. 停止保护：加入最大轮数、模型和工具超时、取消入口及明确停止原因。
  8. 验收记录：保存每轮 Context 摘要、ToolCall、Result、最终回答、耗时和错误。

10 · 把一次任务接着做

Session、Context 与 Memory：保存了，不等于本轮看见了

昨天整理到一半的周报，今天说“继续”，程序怎样知道从哪里接上？

从周报开始拼出本轮请求记录存在哪里四类记忆

先记住三个动作

保存记录 → 选出本次需要的材料 → 发给模型。这是三件事。程序保存过的信息，只有被选中并实际发出，才会成为模型这一轮的依据。

① 先做一件具体的事：整理项目周报

教学解释第 10–16 章用下面这个假想任务贯穿。路径、内容和运行记录只为解释原理，不是仓库里的真实文件，也不是新增开发要求。

“根据本周计划和会议记录整理周报。只读已授权的资料，不要改动原文；预算没有依据就标成待确认，不要猜。先给我预览，确认后再保存为 reports/weekly.md。”

假设你在一个叫“本周周报”的对话中提出要求。程序依次记下：

  1. 你说了什么：上面的任务和限制。
  2. 模型要求做什么：请求读取计划文件，而不是直接编一份周报。
  3. 程序实际做成了什么：工具读到了计划；会议记录还没读完；预算文件读取失败。
  4. 目前停在哪里：预览还没整理好，没有获得保存确认，更没有生成周报文件。

这一整段连续交互及其记录，属于一个会话（Session）。一次“继续整理”的执行过程叫一次 Run；同一个会话可以有多次 Run。你看到的聊天文字只是会话的一部分，工具请求、执行结果和任务状态也要留下。

现在你说“继续”。模型不会因为对话框标题没变，就天然知道前面四件事。程序必须把相关记录放进新的请求。放进去的这份材料，就是本轮的 Context（上下文）。

② 亲手拼一次请求：保存 100 条，可能只取其中一部分

假设会话已经保存了 100 条记录，其中有早期闲聊、重复读文件结果，也有当前周报要求。负责挑选和组装材料的那段程序叫 Context Builder，意思就是“本轮材料组装器”。它不是模型自带的永久记忆。

程序保存或配置了什么本轮怎样处理（教学策略）为什么
用户本次要求与“不要改原文”等限制保留原意，放入请求否则可能完成了错误的任务
刚才的工具请求与返回内容关联保留；必要时裁剪过长正文让模型知道查到了什么、哪里失败，避免孤立的工具结果
很早的重复讨论预算允许可保留；太长时用有依据的摘要替代为继续工作需要的信息腾出空间
另一个会话里的聊天不自动混入会话需要隔离，不能串任务；跨会话使用要有明确的相关性与权限
系统规则、可用工具说明和参数格式随本轮配置加入告诉模型要遵守什么、有哪些动作可以请求
 
本轮发送的材料（示意，不是某个 API 的精确报文）
├─ 系统规则与本次 Agent 配置
├─ 用户任务：整理周报；不改原文；预算不猜；确认后才能保存
├─ 当前状态：计划已读；会议记录未读完；预算读取失败；尚未保存
├─ 相关近期消息、工具请求及对应结果
└─ 本轮可用工具：用途说明 + 参数格式

如果需要，也可加入：
相关的会话摘要、长期记忆、项目约定、Skill 方法说明

选取标准由项目代码和配置决定：相关性、继续任务的必要性、权限边界、可容纳的长度都要考虑。不是固定“只选最后 10 条”，也不是一定不能发送全部 100 条。如果全部相关且放得下，可以全发；只有检查实际请求，才知道这一轮究竟看见了什么。

不要把这一步想复杂

短对话可以直接把 Message List（按顺序保存的消息列表）继续发给模型，形成短期连续性，不需要先做摘要，也不需要先建立长期记忆。历史太长才进入第 11 章的问题。

③ 今天关闭程序，明天还能继续吗？取决于有没有保存到磁盘

只放在运行中程序内存里的消息，程序结束后可能就没有了。写入数据库等磁盘存储，才有机会在重启后重新加载。重新加载后仍须组装请求，不是数据库直接把记忆塞进模型。

summary便于续做的会话摘要哪些已完成、哪些没做、下一步是什么

Artifact 在这里就是生成出来的文件等交付物，不是一个神秘模块。设计建议 SQLite（本地文件型数据库）保存结构化记录，交付物文件单独放在 Workspace（项目工作目录）中，记录里保存它的索引或路径。

④ 为什么还会出现四种 Memory？它们是在给“保留哪些信息”分类

Memory（记忆）是让信息以后还能被利用的机制。既包括近期消息，也可以包括加工后的摘要和跨会话事实；不是要求所有信息先经过一个叫 Memory 的程序再进入 Context。

  • Short-term Memory，短期记忆：这轮带上的近期消息，例如刚才读文件的结果。
  • Session Memory，会话记忆：“本周周报”会话的摘要和任务状态，例如还差会议记录没读完。
  • Long-term Memory，长期记忆：以后其他会话也可能有用的稳定信息，例如你明确要求周报先列风险。
  • Workspace Memory，工作区记忆：这个项目的约定和经验，例如周报统一放在哪个目录。

会议 02 用“短期 / 长期”两类方便入门，设计文档分成以上四层方便实现，粗细不同，并不冲突。Session 回答“记录属于哪段交互”，Memory 回答“哪些信息以后如何复用”，Context 回答“本轮实际发了什么”。它们不是三个互斥的文件夹。

到这里，你应当能指认三样东西

在执行记录中找出会话保存的内容；在请求记录中找出模型本轮收到的内容；说明二者为什么不一定相同。第一切片用内存消息就能验证回填；Phase 2 再验收 Session、Message、ToolCall、AgentRun 的持久化、恢复与简单摘要；Phase 7 完善长期记忆的查看、编辑、删除。向量检索不属于首期必需。

11 · 历史太长时继续做

上下文压缩：留下能接着工作的交接单

对话越来越长，删掉一部分之后，怎样不把“还没做”误当成“做完了”？

为什么要压缩对比两份摘要程序怎样处理怎样验收

这章不是教你写得更短

压缩是在有限的请求长度里，保住下一步做事的依据。好的摘要像一份可以接班的交接单：目标没变、进度没乱、限制还在、已知与未知分得开。

① 沿着上一章：不是数据库满了，是下一轮请求装不下了

你为了整理周报，反复补充资料、读文件、纠正内容。会话可以保存很多记录，但模型一次能接收的内容有长度上限，叫上下文窗口。衡量文本长度常用 Token，可暂时理解为模型处理文字的小单位；它不严格等于一个字或一个词。

所以问题不是“把数据库清空”，而是“这次给模型的材料怎样缩小”。原始记录通常继续保留；下一轮请求可以改为较早记录的摘要，加上必要的近期消息。摘要也占长度，系统规则、工具说明和其他材料也要算进去，还要按模型接口的限制为输出留空间。

会议 02 建议每次请求前估算占用，并举了达到约 80%时压缩到约 30%的例子。两者都不是已确认的项目配置，且原话没有明确“30%”以原文长度还是窗口总量为分母。不能据此直接写死生产参数。

② 摘要好不好，看接班的人会不会做错下一步

教学解释仍是第 10 章的假想周报。先把压缩前的关键事实列出来：

用户要求：先预览，确认后保存；不得改原文；预算缺依据就待确认。
工具返回：计划已读取；会议记录只读取了前半部分。
工具报错：预算文件不存在。
任务状态：正在收集会议依据；尚未生成完整预览。
文件状态：reports/weekly.md 只是计划保存路径，尚未创建。
下一步：读完会议记录，再整理预览；预算仍标待确认。

坏摘要：短了，却改变了事实

“已整理项目资料，周报基本完成，预算后补，接下来保存 reports/weekly.md。”

这句话把“会议只读一半”藏掉了，把“预览还没完成”变成“基本完成”，还跳过了用户确认。模型如果只看到它，很可能直接请求写文件。

可续做的摘要不一定漂亮，但必须把这些区别写清楚：

任务：本周项目周报（以下字段为教学示意，不是已定接口）

goal / 目标：
  基于本周计划和会议记录整理周报，先给用户预览。

constraints / 用户限制：
  只读授权资料；不改原文；预算无依据则待确认；
  未获用户确认，不保存。

actions / 已采取行动：
  已读计划；会议记录读到一半；尝试读取预算文件。

progress / 分项进度：
  已完成：读取计划。
  进行中：收集会议依据，剩余部分未读。
  未开始：完整预览、用户确认后的保存。

results / 已确认结果与产物：
  计划内容已取得；完整周报尚未生成。
  目标路径是 reports/weekly.md，文件尚不存在。

blockers / 失败与缺口：
  预算文件不存在；目前没有可用于填写预算的依据。

nextSteps / 下一步：
  读完会议记录 → 整理预览；预算标待确认；
  用户确认后才可进入保存步骤。

lessons / 继续时要避免：
  不重复把“找不到预算文件”当作预算为零；
  不把目标路径当成已经生成的文件。

这里的“结构化”只是把不同性质的信息分栏写清楚，不是要求你先学一种复杂格式。目标、行动、进度、结果、阻塞、下一步、经验对应 goal/actions/progress/results/blockers/nextSteps/lessons；教学中单列 constraints，是为了不把用户限制埋在长段落里。

如果历史里有“周报、报销、客户回复”三个具体任务，应分别交接，不能只按“写作类、财务类”粗分。会议强调的是按具体任务，不是按任务类型。已完成任务可侧重最终结果与经验；进行中、未完成任务要多保留续做所需的上下文。

③ 程序不是按下“压缩”就算完了，而是做这五步

  1. 组装前算一算：程序估算本轮所有材料的长度，判断是否接近预定上限。尚未接近时，不必每轮都摘要。
  2. 划清压缩范围：哪些较早记录交给摘要，哪些近期工具往返和限制直接保留。不能把所有内容不加区别地截掉尾巴。
  3. 请求模型写交接单：把要压缩的记录和要求一起发给模型，例如“逐任务区分已完成、进行中、未开始；保留限制、错误和路径”。会议说简单时可用一次模型调用，复杂时也可以用一个有步骤的 Loop 完成。
  4. 检查交接单：程序可以检查字段是否存在；关键事实和进度是否正确，还要与原记录对照。字段齐全不代表语义正确。发现缺漏，应补回有关原文或修正摘要，不能盲用。
  5. 再发下一轮请求：把通过检查的摘要、必要近期消息、规则和工具定义组装成新 Context。模型据此继续读会议记录，而不是从头猜发生过什么。

也就是说，压缩发生在下一次模型请求之前，影响的是模型接下来收到的材料。它不是在改模型的大脑。需要排查错误时，应能回到原始会话，找到摘要究竟漏了哪条事实。

④ “节省了多少”与“还能不能做对”要分开算

下面只演示算术，不解释会议里 30% 的分母：假设同一轮已组装输入从 8,000 Token 变成 3,000 Token，输入减少了 5,000 Token，节省比例是 5,000 ÷ 8,000 = 62.5%。这不是测得的项目结果。

但写摘要本身也会调用模型、花时间和 Token。因此“下一轮输入变少”不等于“整个任务总费用同样下降 62.5%”。还要统计摘要调用、后续重复读取、修错等成本。

然后做一次同题对照：把同一个任务停在压缩点，一次用原材料继续，一次用摘要继续。检查是否都去补读会议记录、是否保留预算待确认、是否仍等用户确认再保存。这里的“下一步一致”是任务方向和状态一致，不要求回复逐字相同；同样合理的工具顺序可以不同。

会议中，用户追问策略来自人类经验还是模型探索，工程师回答两者都有，最后要靠工程实践与评测。评测基准（Benchmark）就是用于稳定比较的同一组任务和判定标准。如果只奖励“摘要短”，漏掉重要限制的坏摘要反而可能拿高分。

这一章的验收不是“压缩器跑通了”

至少同时记录：输入节省、总调用成本、关键事实保留、分项进度是否正确，以及任务能否继续完成。有限样例不能保证未来零损失；也不能没验证就宣称成功率不受影响。发现某策略明显伤害任务成功，应调整或暂不采用，而不是为了省 Token 强行上线。

后续验收题：现在用这份交接单回答
  1. 同一长任务压缩前后，下一步行动是否一致？
  2. 已完成、进行中、未开始三类任务是否被正确区分？
  3. 用户限制、失败原因和 Artifact 路径是否仍在？
  4. 压缩节省了多少 Token，是否以任务成功率为代价？
展开答案：每道题到底在检查什么
  1. 检查能否在同一个位置接着做。本例应补读会议记录，而不是直接保存。核对目标、已做动作和真实结果；“摘要说下一步没变”不算证据，还要观察继续执行的实际选择。
  2. 检查每个具体子任务，而不是整件事笼统写“处理中”。读取计划已完成；会议依据收集中；预览和保存未开始。一次工具成功，不等于整个周报完成。
  3. 检查防止走错路的三类信息。限制是“不改原文、先确认”；失败原因是“预算文件不存在”，不是“预算为零”；Artifact 路径是交付物的实际位置。本例只有目标路径，必须注明未生成；若已生成，还要保留真实路径和是否核验。
  4. 检查节省与质量两笔账。示例中单轮输入节省 62.5%，但要另计摘要成本，再用相同任务比较成功情况。不能把“最短”当唯一目标，也不能只凭一份看起来不错的摘要保证成功率。

12 · 下周不必全部重说

长期记忆：哪些事值得留下，下次又怎样取出来

新开一个会话说“按我习惯的格式写周报”，为什么有时知道，有时不知道？

跨周发生了什么怎样写入怎样取回与知识库的区别

这次解决的是另一个问题

第 11 章解决“当前任务太长，如何接着做”；这一章解决“未来别的会话，如何复用有用信息”。长期记忆不是保存一次就自动生效，而是保存后，还要按需取回并送进模型请求。

① 下周的新会话，不能直接继承上周整个对话

教学解释假设周报已经在你的确认后完成。你补充一句：“以后周报都先写风险，再写进度，尽量简洁。”下周新开会话，你只说“整理本周周报”。

有三种不同的信息，不应混在一起：

  • 值得跨周保留的偏好：你明确表达的“先风险、后进度，尽量简洁”。
  • 属于上周的事实：上周预算文件缺失、上周周报的路径。可以留档、按日期检索，但不能冒充本周仍然如此。
  • 不能当成事实的猜测：“用户应该不关心预算”。这是推断，不是你说过的话，更不能据此长期删掉预算信息。

会议 02 提到一种起步方法：将用户偏好、画像和客观事实整理到本地 memory.md。它就是一个可读的 Markdown 文件，不是特殊的大脑文件。画像也必须有依据，不能因为叫“记忆”就把猜测写成真相。

② 第一次留下记忆：从原记录到 memory.md

  1. 选时机：一段会话告一段落，或到达约定的周期事件时，由程序启动整理；并非每句话都必须触发。
  2. 给材料：程序把有关会话记录交给模型，要求提取值得以后复用的信息。没有提供的记录，模型不能凭空看见。
  3. 产出候选条目：模型提出“周报先风险后进度”等内容；暂时性事实保留时间和来源，未确认的内容不能升级为稳定事实。
  4. 检查再写入：按设定的规则检查依据、敏感性和冲突，再由受控工具代码保存。不能因为是记忆文件，就跳过正常文件权限。
  5. 持续维护：你以后更改偏好，要能更新或删除旧条目。会议确认这是持续写入和整理，不是只生成一次文件。
memory.md 的教学条目（不是已确定的存储格式）

偏好：周报先风险，后进度；文字简洁。
依据：用户在“本周周报”会话中明确提出。
适用范围：周报编排。
备注：后续若用户改口，以新要求为准。

不应写成：
“用户不关心预算，以后都可以省略。”

原始会话记录一般仍保留原文，便于核查“这条记忆是从哪里来的”。摘要、提取结果与原始记录不是互相替代关系。

③ 下次使用记忆：两条路，最后都要回到本轮 Context

办法 A：程序在请求之前取出相关条目。新任务是写周报，程序选出周报偏好，和用户新要求一起发送。模型本轮看到了偏好，才可能按它组织内容。会议举过放入系统提示词的做法；实际设计仍应区分可信规则与提取的资料，不能把未经核实的记忆提升成无条件命令。

办法 B：让模型按需请求“搜索记忆”工具。数据多时，不把全部历史塞进请求，而是告诉模型有一个可搜索的工具：

  1. 你要求“总结我本周做了哪些工作”。模型看到任务和搜索工具说明。
  2. 模型输出搜索条件，例如本周日期范围、项目名称、“周报”等关键词。
  3. Runtime 校验请求，工具代码搜索 memory.md 或已授权的原会话记录。
  4. 工具返回相关片段及来源；程序把结果接回原工具调用，加入下一轮请求。
  5. 模型根据实际返回的本周记录总结；没有查到的部分说明缺口，不能把上周事实拼成这一周的成果。

请区分“在哪里”和“写了什么”

如果搜索只返回一个文件路径，模型仍没有看到正文。还要进一步读取所需内容，或让搜索工具直接返回有用片段。保存 → 检索 → 返回 → 加入请求，缺一环都可能表现成“明明记过，怎么又不知道”。

会议用“本周工作总结”解释混合检索：搜索记忆文件，也可以搜索这个周期的原会话。转写里的 grape 紧接“关键词匹配”，疑似指 grep（按文本关键词查找的命令），尚未核实音频，不应断定，更不能解释成图检索算法。先理解“找回有关记录”，不必从向量数据库开始。

④ 知识库也在找资料，但通常不是在记你的偏好

比较个人长期记忆项目知识库
主要来自哪里你的交互、明确偏好、经核实的长期事实项目文档、规范、产品资料等原始材料
这次为什么需要知道你希望周报怎么写知道项目本周实际发生了什么
都要做什么保存资料 → 必要的加工整理 → 检索相关部分 → 放入本轮请求
分别要防什么把一次偏好永久化、把猜测当画像、跨会话过度暴露旧版本混用、片段失去来源、越权读取、遗漏相关材料

这里的分类帮助分清用途，不代表两套技术绝对不能共用。会议认为两者在存储、加工和检索上相似；工程上仍要管理来源、拆分方式、权限与版本。第 16 章再解释“查到资料后再回答”为什么被叫作 RAG。

先验证可用，再增加复杂度

可以先问：一条明确偏好保存后，新会话是否真的收到它？改掉偏好后旧内容是否失效？查错时间、找不到记录、事实冲突时能否说明问题？Phase 7 要支持查看、编辑、删除；秘密和无关隐私不应为了个性化一并放入请求。会议明确 Memory 可以后做，首个 Loop 不以完整记忆或向量检索为前提。

13 · 让动作受到约束

Tool Runtime 与安全：模型想做，不代表程序可以直接做

同一份周报，读取、写入、删除，为什么要走不同的检查？

保存周报的六步工具怎样登记两种模式别混淆边界怎样落实

先从分工理解名字

模型提出动作请求；工具代码做实际动作；中间的程序统一检查、安排执行和收回结果。这段统一管理工具调用的程序，就是 Tool Runtime（工具运行层）。

① 周报预览已经好了，现在能直接保存吗？

教学解释上一章提前看了下周如何复用信息；现在回到上周周报保存之前，拆开看看这一步怎样发生。还记得第 10 章的限制吗？“先预览，确认后再保存”。模型即使已经写出完整内容，也不能替你把这句要求取消。

  1. 模型提出请求：例如写入 reports/weekly.md，并给出内容。这只是请求，还不是文件已存在。
  2. 程序找到对应工具：检查是否有这个工具、是否允许在当前任务使用；不能凭一个名字执行任意函数。
  3. 检查参数和实际目标：路径和内容类型是否符合要求？解析后的真实路径是否在允许范围？写入会不会覆盖原文件？
  4. 检查权限与本次确认：如果还没有用户确认，不能越过“先预览再保存”。界面展示将写到哪里、会做什么，由程序记录确认结果；拒绝就不执行。
  5. 受控执行：满足条件后才调用实际写文件代码；等待超过时限或用户取消，要按约定中止，不能无限挂住。
  6. 如实返回：成功返回实际路径等结果；失败返回原因。程序将结果关联到原调用编号，加入后续消息，让模型知道到底发生了什么，并留下可检查的记录。

工具结果回到第 05 章的同一个 Loop。模型可以根据“写入成功”继续核对，或者根据“用户拒绝”停止保存；不能把“已经发出写入请求”当成“已经生成文件”。

② 工具多了，为什么不能把函数堆在一起就算完成？

会议 01 举例：有 100 个工具，各自对应不同函数。程序需要一张统一的登记表，说明“这个名字对应哪段代码、用途是什么、需要哪些参数”。这张表叫 Registry（工具注册表）。

登记的信息给谁用解决什么问题
名称、用途描述、参数格式（Schema）相关部分进入模型请求知道何时选工具、怎样填写参数；不是过去用过哪些工具的日志
名称对应的真实执行函数程序内部使用模型说“读文件”之后，知道调用哪段代码
风险、权限、来源、执行限制程序执行前及执行中检查参数写对了也不等于有权执行

同名工具要检查和消歧，不能默默覆盖。内置、自定义、MCP 接入的工具，以及 Skill 所依赖的工具，都要在相应能力接入后按统一规则暴露和管理，不能因为来源不同就走一条没有检查的旁路。

工具描述回答“这件工具用来干什么”，Schema 回答“参数有哪些、各是什么类型、哪些必须填”。例如“读取已授权文本文件”是用途；“path 必须是字符串”是参数格式。它们帮助模型提出请求，真实函数实现仍由程序执行，不必把整个函数源代码放进 Context。

登记之外，统一运行层还负责执行、取消、超时与并发限制，控制返回长度、必要时截断并指向完整 Artifact，统一成功/错误结果，以及日志、事件与 Trace。Trace 就是能按时间和调用编号还原过程的记录。结果被截断时应说明，不让模型误以为看到了全文。

③ “能做哪些动作”和“配了多少能力”，是两条不同的轴

先看设计文档中的风险分级，不是把所有动作一律弹窗：

  • 低风险：例如列目录、读取允许范围的文件，可以自动执行。这里的“可自动”不等于可以读任意路径。
  • 中风险：例如写文件、安装依赖、网络请求，根据设定策略决定是否确认；本例用户额外要求先确认保存，就必须遵守。
  • 高风险：例如删除文件、执行危险 Shell 命令、发送外部消息，设计要求必须明确确认。确认不能绕过其他硬性权限限制。

会议用“读通常可用、写大部分时候先审批、删除每次审批”帮助理解风险差异；设计文档则给出上述三级策略。具体产品应把策略说明白，而不是让模型临时猜哪些危险。

会议里的两组名字实际在回答什么怎样理解
Read Only / Workspace Write / Full Access允许动作到哪里？只读 / 工作区内写入 / 更宽的访问权限；名称本身不能代替具体边界
极简模式 / 标准模式这一套 Agent 配了什么？工具数量、提示词、框架能力等配置差异；会议称为 Harness 模式

Harness 在这段讨论里，可先理解为围绕模型配置起来的一整套工具、指令和运行安排。会议的极简例子只有 Bash（执行命令）和编辑两个工具，配短系统提示词；工程师认为这类设计快、便于二次扩展。标准模式则可能带更多工具，包括 Web Search。

这些是会议中的产品例子与工程观点，不是本项目必须提供两种模式的承诺，更不是“工具少就安全、工具多就一定更好”。一个命令执行工具也可能有很大权限；工具数量和权限大小不是同一回事。

④ “请小心”不是权限控制，真正的拦截发生在执行之前

假设模型请求改写原始会议纪要，虽然路径存在、参数正确，也违反了用户“不改原文”的限制。正确结果是程序阻止写入并说明原因，而不是先写完，再在界面提醒你。

  • 工作区边界：检查真实目标，不能只看路径字符串表面是否以某个目录开头。
  • 动作透明：需要确认时展示关键参数、目标和影响；不要只弹一句“是否允许使用工具”。
  • 凭据隔离：API Key 等秘密由安全配置提供，不混进提示词、文件结果或日志；必要的日志要脱敏。
  • 来源与会话隔离：外部工具返回和文件正文是资料，不能自己变成新增授权；一个任务的结果不能串到另一个任务。
  • 执行有边界：设置超时、取消、并发和结果大小限制。界面取消后，不能继续悄悄执行新的危险动作。

这些约束属于程序和运行环境的责任。定时任务、后台任务也应走同一套限制，不能因为用户当时没有盯着界面就自动获得更大权限。

本章先学会判断，不要求现在做完全部工具平台

你应能区分“模型请求被拒绝”和“工具执行后失败”，并确认两者都没有伪装成功。设计的 Phase 3 再系统验收危险操作确认、工作区边界、超时取消、错误后调整、长结果处理和统一记录。是否进入该阶段，以当前授权和阶段记录为准。

自检：换成读、写、删，再走一遍

  2. 界面给了“拒绝”按钮，是否就证明实际权限安全？
  3. 极简模式只有两个工具，是否等于 Read Only？

  4. 要。错误是实际执行结果，要关联原调用回填。模型才能区分参数错误、权限拒绝和文件缺失，选择修正、询问或停止；不能无限重试同一个失败动作。

14 · 证明做完，而不是说做完

完成验证与评测：怎样知道这次真的交付了

Agent 说“周报已完成”，你应该找哪几条证据，而不是只看这句话？

四个不同状态完成前怎样核对测试证明什么什么时候停止

先定义完成，再让程序检查

模型说“完成”是一个判断，不是完成的证据。要把用户要求翻译成可检查的条件，再核对实际文件、工具返回或运行结果；没做的检查，就不能写成已经通过。

① 同一句“好了”，可能掩盖四个完全不同的状态

教学解释继续周报案例。假设你已看过预览，并明确同意保存。

实际发生的事目前能说什么还不能据此说什么
模型输出写文件请求“准备保存”不能说文件已经写入
工具返回写入成功“文件已写入指定位置”不能仅凭这个断言内容完整、准确
重新读取文件，并对照本周资料检查“已核对这些具体要求”没检查的要求不能冒充通过
本次约定的完成条件都有证据“本次任务完成”，说明剩余限制不能扩大成“系统处理所有任务都可靠”

本例可以预先约定：本周计划和会议记录都已读取；周报包含有依据的进度和风险；预算仍标待确认；原文没有改动；已获保存确认；文件确实在指定路径。这里是教学条件，不是要求所有任务都跑同一组检查。

如果用户只要求预览，那么完成预览就可能已经满足任务，不能擅自增加写文件来“证明做事”。验证动作也不能越过授权。

② 在准备结束时，插入一次有目标的核对

会议 01 讨论了一个可选增强：主模型准备结束时，程序把检查要求加入同一个主循环，让它带着实际证据再判断一次。用周报来理解：

  1. 先有完成条件：明确本次要检查哪些内容，不等最后才无限添加标准。
  2. 模型提出结束：比如准备回复“已保存周报”。这时程序检查，本次需要的核验是否已经完成。
  3. 如果证据还缺，追加具体检查：例如“请读取刚生成的文件，核对会议依据和预算标记”，而不是空泛地说“再检查一下”。
  4. 执行相应工具：实际读取文件或运行已获授权的验证动作；成功或失败都回到同一个消息链。
  5. 据证据作分叉：通过则记录“已核验”，允许结束；发现缺漏且仍在授权和预算内则修正；缺资料或权限则说明无法完成的部分。
  6. 停止条件仍有效：达到轮数/时间/费用限制，或用户取消，就按规则终止，明确未完成检查。不能因为叫“验证”就无限循环。

已通过的核验要有状态记录。否则每次模型准备结束，程序都再插入同一句检查，就会永远结束不了。也不是必须另请一个模型才叫验证；工具结果与明确条件才是关键。

会议的完整进阶例子：代码任务怎样加检查？
  1. 请求先到一个小模型，识别是不是 Coding（编写代码）任务；其他任务可走别的策略。
  2. 主模型处理代码任务，实际编辑或写入文件。
  3. 当主模型准备结束时，程序追加针对代码的检查要求。
  4. 可能重新读取文件、实际运行代码；涉及前端时，还可渲染页面并查看截图。
  5. 这些检查结果回到原主 Loop；模型再判断是否有问题，程序按状态和预算允许结束、修正或如实停止。

这是会议讨论的进阶设计思路，小模型分类、结束前检查都不是第一切片的前提，也不是已经确认有一个通用准确率。不能把这段例子缩成“接一个验证模型就解决了”。

会议还指出，判断效果受两件事影响：模型本身的能力，以及这次实际看见什么。应用可以选择合适模型、改进 Context，却不能通过改 Runtime 就直接改掉模型本体的能力。不给目标、限制、结果和错误，模型很难凭空判断是否完成；给齐材料也不是绝对正确的保证。

③ 一次完成验证，和比较系统有没有进步，不是同一件事

刚才检查的是“这次周报是否达标”。评测则是用一组事先确定的任务和标准，比较不同版本的整体表现。设计文档把测试分成三层：

原设计名称用周报说人话通过后能证明什么
Unit，单元测试单独给权限检查函数一个越界路径，确认它拒绝；给参数校验错误类型；检查状态和 Context 组装这一个小部件在这些条件下正常，不代表真实模型会做完整任务
Integration，集成测试把 Provider、工具、数据库或 MCP 的连接部分接起来，检查调用和结果能传递被测连接能协作；用模拟返回的测试，不证明真实服务效果
Scenario，场景测试从用户提出周报要求，一直观察到回答或文件交付，以及缺失信息时的处理该代表性任务在所测条件下能完成；仍需注明模拟还是实际运行

例如两个压缩策略：A 的摘要极短，但丢了“不覆盖原文”；B 稍长，却保住限制。若只考“摘要短不短”，A 得分更高；若考“最终是否正确且遵守限制”，A 就失败。错误的 Benchmark（固定比较题及标准）会让你以为更好了，实际却更差。这是会议特别提醒的问题，不是已测得的 A/B 实验结论。

保留原设计的七项风险顺序：后续按阶段使用
  1. Agent Loop 能否正确结束。
  2. 工具参数、权限和错误能否正确处理。
  3. 会话重启后能否恢复。
  4. 不同 Provider 的消息和 Tool Schema 是否保持一致。
  5. MCP 断线、超时和外部进程异常。
  6. Cron 重复、漏触发与并发冲突。
  7. 上下文裁剪是否丢失关键任务状态。

它们对应完整路线的风险，不是现在必须一次做完的清单。没进入 MCP 或 Cron 阶段，不应为了读懂本章就新增开发阻塞。

④ 验收也要能结束：不要把三个结论混成一个

  • 闭环成立：模型自主请求工具，程序受控执行，真实结果回填，模型据此回答或合理结束，记录能还原过程。
  • 真实任务有用：代表性真实任务的结果准确、完整、值得使用，需要相应任务证据。
  • 达到发布质量：要看既定使用范围内的稳定性、安全和体验，不是一个成功例子就证明。

第一切片关心实际读取、工具请求来源、权限、原调用关联的成功/错误回填、下一轮收到结果、回答有原文依据、轮数/超时/取消边界与 Trace。固定样例通过、关键证据齐全，就关闭那个范围；后续质量问题如实记录，不能悄悄扩成无止境的原阶段验收。

你要能追问的不是“测了多少”，而是“这条结论由什么支持”

保存成功看工具结果；内容准确看原文对照；模型确实看到结果看实际请求。模拟、离线重放、真实 API 运行、AI 复核和用户验收要分别标明。当前项目阶段以当前阶段记录为准，本章教学不要求重跑已完成里程碑。

自检：哪句话需要哪条证据？
  1. write_file 返回成功，就能说周报内容完全正确吗？
  2. 为什么检查完还要把结果带回下一轮，而不是只在后台跑一下？
  3. 有一个小模型负责分类或检查，是否就能保证任务完成？
  4. 已完成固定验收，又发现一个新边界例子，是否必须无限继续？
展开答案与原因
  1. 不能。写入成功证明动作完成；周报是否遗漏会议内容、是否乱填预算，还需要与任务要求和来源核对。正确描述“保存成功，但某项未核验”，比扩大结论可靠。
  2. 因为模型必须知道核验的实际结果，才能基于证据继续或结束。后台跑过但没有回填，对下一轮模型等于没有提供信息；程序也需要记录通过、失败或未完成状态。
  3. 不能。分类只是选策略，模型自检也会出错。还要有实际文件或运行证据、明确标准、权限约束，以及不会无限重复检查的终止规则。

15 · 换模型，不重写整个助手

Provider：把同一份任务接到不同模型服务

周报任务、工具权限和保存流程没变，换一家模型服务，为什么仍需要适配代码？

先分清四个东西走一趟来回还要对齐什么怎样分阶段验证

先理解它要挡住什么变化

不同模型服务可能用不同的请求和返回格式。Provider 适配层负责翻译这些差异，让核心循环仍按同一套方式收发消息、处理工具请求。它统一接口，不保证不同模型同样聪明或每次输出一样。

① 先分清：模型、服务、API 和适配层

  • 模型：根据输入生成回答或工具请求的能力本体。不同模型的表现可能不同。
  • 模型服务：把模型运行起来，供外部程序调用的系统；可能是云服务，也可能在本地。
  • API：程序与服务约定的调用入口和收发格式。你的程序按约定发送材料，服务按约定返回结果。
  • Provider 适配层：你这个 Agent 项目里的连接代码，负责把内部格式和具体服务格式相互转换。不是模型本身，也不是聊天页面。

会议特别区分了两件事：在现成应用里切换模型，是使用别人已经接好的系统；自己做 Agent，则需要接 API，并自己负责历史、工具、权限与循环。接通一个 API 是起点，不是整个 Agent 已经完成。

② 同一个读文件请求，走一趟完整来回

教学解释还是周报任务。以下“服务 A / 服务 B”是假想服务，只说明格式差异，不对应任何厂商当前接口。

  1. 核心先准备统一材料：用户要求、相关历史、当前进度、工具的说明和参数格式。
  2. 适配层翻译后发出：选择服务 A，就按 A 的协议发送；换服务 B，就由 B 的适配器处理。比如两家服务的消息字段、工具字段、角色标记可能不同。
  3. 模型服务返回：本轮可能是直接回答，也可能是“请求读取会议文件”。服务返回的包装格式也可能不同。
  4. 适配层翻译回来：转成内部统一的文本回复或 ToolCall，保留工具名、参数和调用关联信息。
  5. 核心继续原循环：如果是 ToolCall，就交给工具运行层校验与执行，再把结果送入下一轮；如果是可结束的回答，就按既定完成规则结束。

⇄

这里的 Agent Core 就是负责消息和决策循环的核心部分。目标是换服务时更换适配器和配置，不到核心里到处写“如果是 A 就这样，如果是 B 就那样”。工具权限、真实文件执行、结果回填和取消边界仍然属于你的 Runtime。

③ 为什么适配层不只是“填一个地址和 Key”？

要处理的差异不处理会怎样
消息、工具 Schema 和工具调用/结果格式模型不认识工具，或返回的调用丢失关联，无法继续原任务
流式输出：把逐步到达的内容变成统一事件界面和核心可能只能理解某一家服务；工具参数未接收完整就误执行
Usage、Token 和成本信息难以比较总消耗；服务未提供的数据必须标未知，不能编造金额
错误、限流、超时、重试网络失败被当成成功，或无限重试；模型请求失败不能假装工具已经执行
能力声明把需要工具调用的任务交给不支持该能力的服务配置，直到运行时才出错
Key、Base URL、模型参数凭据泄露或连接错环境；这些是程序配置，不该作为聊天正文发送

Base URL 是服务入口地址，Key 是访问凭据；本章不需要你填写，更不需要将它们贴进对话。重试也应有限次、有限时，并与取消规则配合。

原设计的四个接口名，现在可以逐个读懂
  • chat(request)：发送一次对话请求，取得统一结果；request 指本次请求材料。
  • stream(request)：接收逐步返回的内容和事件，而不是等全部输出完才显示。
  • listModels()：列出这个 Provider 可用的模型。
  • getCapabilities(model)：说明指定模型/服务配置支持哪些能力，例如是否支持工具调用。

这些是设计文档中的接口约定，不是让你照抄某家 SDK，也不表示仓库当前已全部实现。具体能力应按 Provider 声明与验证判断，不只按模型名称硬编码。

“支持工具调用”意味着模型/接口能够按约定提出结构化工具请求，还需要你的运行层把请求执行并回填。适配器只能转换协议，不能把一个本来不具备的能力靠字段改名自动造出来。

④ 分两步验证，别为了能换模型先把所有服务接一遍

  1. 先一个云端 Provider：确认 API 的输入输出，再接读文件和历史回填，让一条真实工具链路成立。不要一开始同时排查多个服务差异。
  2. Phase 4 再接第二个：可以是兼容云服务或本地服务；验收目标是无需修改 Agent Core 就能切换，同时正确处理各自能力与协议差异。

对照时仍用相同的周报任务：两边都能正确提出工具请求、收到真实结果、按边界结束；输出文字不必完全一致。若 B 不支持必要能力，要明确报告不支持，不能静默丢掉工具定义却宣称切换成功。

这章学完，你应能画出“哪里变，哪里不变”

改变：服务地址、凭据、模型配置、请求/返回适配。保持：任务目标、核心循环约定、工具权限、结果关联和完成标准。会议中的低成本 API、充值和具体价格属于当时建议，不是当前采购依据；本章不据此推荐购买。

自检：换一家服务再做同一份周报
  1. 换模型后，是否应该把读文件权限检查也重写一遍？
  2. 服务 B 的回复格式与 A 不同，应该优先在哪一层处理？
  3. 第二个 Provider 能正常聊天，就证明 Phase 4 通过了吗？
展开答案与原因
  1. 通常不应该。换模型服务不改变用户允许读哪些文件。权限约束留在统一工具运行层；服务的协议差异由适配层处理。
  2. 在 B 的 Provider 适配器。将返回转换成核心能理解的回答、ToolCall 或错误。若核心到处依赖 B 的专用字段，说明隔离还不充分。
  3. 没有。还要检验无需修改 Core 的切换、工具请求和结果关联、能力差异，以及相关流式/错误等约定。普通文本聊天成功只证明了其中很小一部分。

16 · 有明确需要，再加能力

MCP、Skill、RAG、Cron：四个不同问题，接回同一个流程

资料在外部、方法要复用、历史太多、希望定时做——分别该补哪一块？

先认问题外接能力复用方法先查资料定时发起

不要同时背四个定义

先指出当前缺什么，再决定加哪一块。它们并不是四个互相替代的 Agent，也不是必须全部具备，才能跑通一次模型调用工具的闭环。

① 仍然做周报，只是逐个增加现实需求

教学解释前面的周报已经能手动发起、读取本地资料、预览、确认并保存。现在分别遇到四个新问题：

你遇到的具体问题补什么接在原流程哪里

每次都要重复解释“如何整理一份合格周报”Skill：复用一套方法说明及所需材料相关方法加入 Context；其中用到的工具仍走原运行层

同一项目可能需要其中几种，也可能暂时一种都不需要。接下来每次只增加一个需求，先看它为什么出现，再看名称。

② MCP：别人做好的能力，怎样接进你的工具系统

假设项目管理系统里有“查询本周事项”的能力，但你的 Runtime 只会读本地文件。你不想为每个外部系统重新设计一套连接方法，就可以考虑 MCP：一套让应用与外部能力服务按共同约定交互的协议。

先认识两端：对方提供能力的程序叫 MCP Server；你的项目中负责连接它的部分叫 MCP Client。这里 Client 是程序角色，不是你的客户。

  1. 配置并连接：Runtime 按配置连接或启动外部服务，确认来源和允许范围。
  2. 发现它提供什么：取得 Tools（可执行动作）、Resources（可读资料）、Prompts（可复用提示模板）。三者不同，不能全部当成可随意执行的函数。
  3. 接入内部管理：外部工具的名字、用途和参数格式转换后登记进工具系统；同名冲突、可用性与权限需要处理。
  4. 让模型看到可用工具：本轮请求带上相关工具说明，模型才能选择“查询本周事项”，并提出参数。
  5. 执行并回填：统一工具运行层先校验，再通过 MCP Client 请求外部服务；取得结果后按原调用返回，模型才能据此写周报。

MCP 负责接通外部能力，不负责替你决定业务目标，也不会自动放宽权限。外部服务断线、超时或进程退出，要返回可解释错误并处理恢复，不能当作“事项列表为空”。发现工具、接通一次，也不等于它在真实任务中始终可用。

原设计里的接入细节，现在怎样理解？

stdio 表示通过进程的标准输入/输出传递消息，常见于由本地启动的外部程序；HTTP 表示通过服务请求传递。项目设计要管理服务配置、启停、发现、适配，以及断线、超时、进程退出。来源信任、权限、日志仍归入统一边界，MCP 不直接侵入 Agent Core。

这些是目标设计项，并不表示本手册展示了一次已经完成的真实 MCP 接入。

③ Skill：工具告诉它“能做什么”，方法包告诉它“怎么做好这类事”

假设每周你都要说：“先看计划，再读会议；先列风险，再写进度；没依据的预算标待确认；检查来源后再交付。”把这套稳定做法整理起来，就是 Skill 的一种用途。

会议与设计讨论的 Skill 不是一个魔法函数，而是可加载的方法包。可以包含 SKILL.md 或清单、说明文字，也可带 tools / prompts / scripts / references，分别是所需工具、提示模板、脚本和参考资料。

  1. 安装或放入方法包：记录名称、用途、版本、所需工具和环境。加载文字成功，不代表它需要的外部工具也安装好了。
  2. 在合适任务触发：用户明确选择，或按设定规则匹配到“整理周报”这类任务，不是所有任务都加载全部方法。
  3. 把相关步骤送给模型：方法说明进入本轮 Context，模型据此安排读资料、整理、检查等动作。
  4. 动作仍受控：读文件和写周报继续走原工具运行层。方法包要求的权限若没有授权，不能自行提升。
  5. 实际看结果：检查是否按约定结构完成、有无遗漏来源，而不是只确认“SKILL.md 已读取”。方法变更还要管理版本和依赖。

用一句话区分：Tool 是一次具体动作；Skill 是完成一类任务的方法；Agent 是结合任务、方法与可用动作，循环推进的执行者。Skill 可以依赖工具，不等于工具本身；加载一个 Skill 也不是新建了另一个独立 Agent。

④ RAG：资料太多时，先找出相关的那几段再回答

假设有一年会议记录，你只问“本周哪些事项延期”。一次塞入全年资料既长又容易干扰。先找本周及延期相关片段，再让模型据此回答，这种安排叫 RAG（检索增强生成）。“检索”就是找资料，“增强生成”就是把找到的资料作为回答依据。

它通常包含：保存原始资料 → 需要时切成便于查找的小段并保留来源 → 用日期、关键词等条件找相关内容 → 把片段放进请求 → 模型回答并说明依据。是否使用向量检索，是实现选择，不是理解 RAG 的前提。

有两种常见接法，别误以为只有一条：

  • 程序先查：在调用模型前，程序按任务取出有关片段，Context Builder 把它们组装进去。模型第一次收到任务时，已带有查到的资料。
  • 模型决定再查：模型先看到任务与检索工具，输出查询参数；程序检索，将实际结果回填；下一轮模型带着片段回答。

会议 01 转写中的 reg 结合上下文疑似指 RAG，未据音频核实；当时讲“通过工具参数”的例子，指的是模型自主请求检索这条路，不能推广为所有 RAG 都只能由模型调用工具。

回到第 12 章：“记忆 / 知识库”描述资料的来源与用途，“RAG”描述先找资料再回答的使用方式。记忆文件、会话记录、项目知识库，都可能成为被检索的对象。查到内容还要核对日期、版本、来源和权限；没搜到不等于事实不存在，返回路径也不等于返回正文。

⑤ Cron：把“用户现在发起”换成“到时间发起”

如果你希望每周自动整理周报，需要一段按时间启动任务的程序，叫调度器；Cron 是这里讨论的定时任务机制。它先解决“什么时候开工”，不负责代替模型整理周报。

先保留会议原例：“每天早上 8 点查询黄金价格”。一条任务至少要把下面几件事说清楚：

要指定什么金价例子怎样理解
任务查询黄金价格；实际用哪个报价来源和口径，需要明确，会议未定
时间与频率每天早上 8 点；工程上还要明确时区，不能靠程序猜
运行地点由哪个 Runtime / 工作环境执行，是否有需要的工具权限
会话结果进入哪个会话，是复用还是新建，需要设定
  1. 到达约定时间：调度器发现这条任务该执行了。
  2. 创建一次运行：把任务内容送入指定 Runtime 和会话，作为一个触发来源；可附“定时任务”标签，必要时加入适合该场景的系统指令。
  3. 进入原 Loop：模型决定使用查询工具；程序照常检查权限、执行查询、回填结果。
  4. 根据实际结果交付：有数据才报告所查口径的价格；失败要如实说明，不把昨日结果冒充今日结果。
  5. 记录并通知：保存本次执行状态和历史，按通知策略把结果送给用户；不等于重新训练模型。

因此 Cron 是 Trigger（触发来源），不是另一套 Agent Loop。把任务换成每周周报，也仍要遵守你“先预览、确认后保存”的要求。定时启动本身不代表可以绕过用户确认。

定时任务为什么还要有这些配置？

原设计还列出 Cron 表达式，即把“什么时候执行”写成程序可解析的时间规则。先明确每天 8 点、时区和频率，再由调度配置表达；读懂这里不需要先背表达式语法。

  • 一次性 / 周期、启用 / 停用：避免你停掉了任务，它仍继续运行。
  • 并发：上一轮还没结束时，下一次到点如何处理，避免重复写入或互相覆盖。
  • 超时与重试：服务失败可以按策略有限重试；不能不断重发并造成重复副作用。
  • 历史与通知：区分未触发、运行中、失败、完成，让用户知道实际状态。

未来 Webhook（外部系统发生事件后发来通知）也可作为 Trigger，经同一入口创建 AgentRun。不是收到外部通知就接受其中任意指令或权限。

一句话结论

会议中的企业交付三层逻辑

  1. 需求层：企业是什么行业、什么业务场景、当前生态怎样、底层框架需要解决什么。
  2. 能力层：Agent 能否基于可信外部数据完成有效分析与行动。
  3. 产品层：能力应嵌入对话入口、网页点选、传统表单、工作流节点，还是其他业务流程。

用户用之前的文旅 AI 项目追问企业交付。工程师指出，最核心的是 Agent 的智能能力是否能利用可信数据做有效分析；至于长成智能助手页面、点选式网页还是工作流产品，是应用形态问题。会议还用 GTM 场景举例：AI 可以融入市场营销和销售流程，主要交互未必是对话。

为什么过程轨迹是产品能力

项目不仅要显示最终答案，还要展示会话管理、Context 持久化、工具调用与事件流。对用户，这提供进度、确认和错误解释；对开发者，它揭示执行链路；对企业，它支持审计、信任和故障复盘。设计文档因此把“一切执行均可追踪”列为核心原则。

交互层的责任边界

  • 创建、选择、恢复 Session。
  • 接收自然语言任务，展示流式输出。
  • 展示 ToolCall、运行进度、异常与 Artifact。
  • 处理确认、取消与中断。
  • 不直接编排 Agent Loop。
